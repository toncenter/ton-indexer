# ton-traces: трейсы целиком

Трейс — все транзакции, порождённые одним внешним сообщением (или одной
системной транзакцией). Они могут растянуться на несколько masterchain
блоков. Модуль `map_traces` отдаёт каждый трейс **один раз**, в блоке, где он
закончился, с транзакциями, связанными в дерево. Это базовый пакет: свои
модули строятся поверх `map_traces` (пример — `../ton-big-traces`).

| Модуль | Тип | Что делает |
| --- | --- | --- |
| `store_trace_size` | store (add) | число транзакций каждого незакончившегося трейса |
| `store_pending` | store (set) | первые `max_transactions` транзакций каждого трейса под ключом `<trace_id>/<lt>/<hash>`, пока он не закончился |
| `map_traces` | map | трейсы, закончившиеся в блоке, с транзакциями |
| `map_trace_digests` | map | то же без транзакций: id, хэши, родители, глубины — для проверок |

Как это работает. В каждом блоке TON Firehose у транзакции есть `trace_id`,
а `Block.traces` перечисляет трейсы, закончившиеся в этом блоке, с полными
числами транзакций и сообщений (тот же TraceAssembler, что в индексаторе,
поэтому `trace_id` = API v3). Stores копят трейс, пока он идёт, и удаляют его,
когда он закончился. `map_traces` читает **дельты** обоих stores: удаления
приходят со старыми значениями — это транзакции трейса и сколько их модули
видели.

Ограничения по времени нет: трейс ждёт своего окончания сколько угодно. По
размеру — есть: `store_pending` держит не больше `max_transactions` (1000)
транзакций трейса, остальные только считаются в `store_trace_size`. Без этого
один трейс весны 2020 года (15 063 031 транзакция) занял бы в store, по
оценке, десятки гигабайт и пришёл бы одним сообщением такого же размера; с
лимитом его сообщение — около 5 МБ в JSON.

## Формат

`proto/traces/v1/traces.proto`. На блок — `Traces { seqno, utime, traces }`,
трейсы в порядке `Block.traces`.

`Trace` — то же, что в API v3 (`trace_id`, `external_hash`,
`external_hash_norm`, `mc_seqno_start/end`, `start/end_lt`,
`start/end_utime`), полные `transactions_total` и `messages_total` — даже
когда транзакций в сообщении меньше, — состояние и `transactions`.

`transactions` — плоский список `Node` по lt. Первый — корень, родитель всегда
раньше детей:

| Поле | Что это |
| --- | --- |
| `parent` | индекс транзакции, отправившей входящее сообщение; у корня не задан |
| `out_msg_index` | какое из `out_msgs` родителя — входящее сообщение этой транзакции |
| `children` | индексы транзакций, которые вызвали её исходящие сообщения, по lt |
| `depth` | 0 у корня, иначе глубина родителя + 1 |
| `mc_seqno` | masterchain блок, в который транзакция попала |
| `transaction` | сама `sf.ton.type.v1.Transaction` целиком |

Почему список, а не вложенное дерево: protobuf-декодеры ограничивают
вложенность (prost — 100 уровней), а глубину трейса задаёт тот, кто его
запустил; плоский список читается при любой глубине. По нему одинаково легко
пройти всё подряд (`for node in &trace.transactions`) и обойти дерево:

```rust
fn walk(trace: &Trace, index: u32) {
    let node = &trace.transactions[index as usize];
    // ... node.transaction, node.depth
    for &child in &node.children {
        walk(trace, child);
    }
}
// walk(&trace, 0) — от корня
```

Состояния:

- `COMPLETE` — все `transactions_total` транзакций на месте;
- `TRUNCATED` — транзакций больше `max_transactions`: отданы первые по блоку,
  потом по lt. Родитель каждой из них тоже отдан, то есть это дерево трейса от
  корня, обрезанное снизу; полный размер — в `transactions_total`;
- `INCOMPLETE` — нет начала: трейс начался раньше `initialBlock` модулей.
  С `initialBlock: 1`, как в пакете, не бывает — только в копии с другим
  `initialBlock`.

Лимит — параметр `store_pending`, меняется без пересборки:
`-p store_pending=max_transactions=5000`. Но это другой модуль (другой хэш),
и сервер посчитает его заново с `initialBlock`.

## initialBlock 1 и первый запуск

Все модули начинаются с блока 1, чтобы каждый трейс был виден с начала. Цена:
чтобы отдать трейсы около блока N, серверу нужны состояния stores на блоке N,
то есть пройти всю историю до него. Первый запрос к пакету это и запустит:
tier2 считает сегменты по 1000 блоков параллельно и кладёт в кэш, все
следующие запросы любых пользователей и модулей поверх `map_traces` берут
состояния оттуда. Сейчас (4 параллельных задачи tier2 по умолчанию) это
~250 блоков/с на стадию, две стадии stores на ~101 млн блоков — порядка 9
суток; на сервере с 96 ядрами можно поднять параллельность. Кэш привязан к
хэшам модулей, а в хэш входит wasm: любая пересборка — новый прогрев. Греть
стоит готовый, опубликованный пакет.

Пока кэш не прогрет, для опытов — копия манифеста с поздним `initialBlock`
(трейсы, начавшиеся раньше него, придут `INCOMPLETE`):

```bash
sed 's/initialBlock: 1$/initialBlock: 100050000/' substreams.yaml > substreams-dev.yaml
```

```bash
substreams pack substreams-dev.yaml -o ton-traces.spkg
```

## Сборка и запуск

Как в `../ton-transfers` (rustup с `wasm32-unknown-unknown`, эндпойнт в
`SUBSTREAMS_ENDPOINTS_CONFIG_TON`):

```bash
cargo build --target wasm32-unknown-unknown --release
```

```bash
substreams pack substreams.yaml -o ton-traces.spkg
```

Трейсы, закончившиеся в 300 блоках, коротко (с пакетом из `substreams-dev.yaml`
выше, иначе — прогрев всей истории):

```bash
substreams run ton-traces.spkg map_trace_digests -s 100053000 -t +300 --production-mode --limit-processed-blocks 0 -o jsonl
```

Целиком, с транзакциями (тяжелее):

```bash
substreams run ton-traces.spkg map_traces -s 100053000 -t +10 --production-mode --limit-processed-blocks 0 -o jsonl
```

## Что проверено (2026-10-20)

Проверки — на копиях манифеста с `initialBlock` 100 050 000 и 3 290 000 (код
тот же), плюс пакет как есть на блоках 1–1000.

- **Параллельный счёт = последовательному.** `map_trace_digests` в
  production-mode (stores посчитаны сегментами по 1000 блоков на tier2) и
  прогон подряд от `initialBlock` дали одинаковые 2302 трейса в блоках
  100 053 000–100 053 299.
- **Совпадение с прежним прототипом.** На всех 3300 блоках
  100 050 000–100 053 299 — те же 27 156 трейсов, транзакции и родители, все
  `COMPLETE`. Прототип на этих блоках сверялся с `/api/v3/traces`: 160 трейсов
  совпали, в том числе диапазоны блоков, lt, транзакции и дерево.
- **Поля узлов.** На 376 трейсах целиком (50 блоков): `children` — ровно
  обратное к `parent`, `out_msgs[out_msg_index].hash` родителя =
  `in_msg.hash` ребёнка, `depth` = глубина родителя + 1, порядок по lt.
  Глубина до 27, детей у одной транзакции до 11.
- **Лимит.** С `max_transactions=5`: 231 трейс из 2302 — `TRUNCATED` ровно с
  5 транзакциями и полным `transactions_total`, у всех корень на месте и у
  каждой транзакции есть родитель; на 39 трейсах целиком отданы именно первые
  5 по (блок, lt). Остальные 2071 совпали с полными.
- **Гигант.** Трейс `e887503f…ab94` (весна 2020): в блоке 3 311 405 пришёл
  `TRUNCATED`, 1000 транзакций из 15 063 031, блоки 3 295 399–3 311 405 (16
  границ сегментов). Первая — корень (`trace_id`), дерево целое, все 1000 — из
  первых 17 блоков трейса (3 295 399–3 295 418), глубина до 15. Прогон с
  подготовкой stores на 21 тыс. блоков тяжёлой эпохи — 202 с.
- **С блока 1.** Пакет как есть на блоках 1–1000: 5005 трейсов, все
  `COMPLETE`.
- **Пакет поверх.** `../ton-big-traces` на тех же 300 блоках — те же 200
  трейсов, stores из кэша.

98% трейсов начинаются и заканчиваются в одном блоке, ~2% — в соседнем.

## Открытые вопросы

- Прогрев истории (см. выше) — когда пакет будет готов к публикации.
- Трейсы, которые TraceAssembler так и не закрыл, остаются в stores навсегда
  (до 1000 транзакций каждый). Сколько их за всю историю, станет видно после
  прогрева, по размеру снапшота `store_pending`.
- Транзакции целиком — это трафик клиента; `map_trace_digests` — лёгкий
  вариант, можно сделать промежуточный.
