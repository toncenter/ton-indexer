# ton-webhooks: дизайн

Статус: черновик для ревью, 2026-10-19. Детальные спецификации API и
компонентов — следующим шагом.

Пометки в тексте:

- **Решено** — решение принято.
- **Предложение** — рекомендация, ждёт ревью.
- **Открыто** — требует проверки или отдельного решения.

## 1. Задача

Клиент указывает адреса и фильтры и получает события блокчейна TON, которые
должен надёжно обработать: без тихих потерь, по порядку, с возможностью
восстановиться после своего или нашего сбоя. Сервис рассчитан на все сегменты
сразу — от бота с одним адресом до биржи с миллионами депозитных адресов.

## 3. Гарантии доставки

- **At-least-once.** Повтор батча приходит с тем же `webhook-id`. События внутри
  несут стабильные идентификаторы: хэш транзакции, `action_id`.
- **Строгий порядок в рамках потока подписки** — одного типа событий (§4). В
  полёте не больше одного запроса на подписку. Порядка между транзакциями и
  actions нет: action приходит по блоку завершения трейса и может отставать от
  транзакций на время классификации.
- **Без тихих потерь.** Курсор двигается только после 2xx. Ни отставание, ни
  выход за глубину хранения не приводят к молчаливому пропуску: подписка
  получает явный статус.
- **Задержка** относительно финализации — единицы секунд: для транзакций это
  индексация, для actions — индексация плюс классификация.

## 4. Курсор

### Потоки (Предложение)

Каждый тип событий подписки — отдельный поток со своим курсором и своей
границей готовности (§5). Классификатор работает асинхронно, и единый курсор на
подписку заставил бы транзакции ждать actions. С потоками отставание
классификатора задерживает только actions.

- Для клиента это по-прежнему одна подписка: один URL, один набор адресов,
  один фильтр, одни статусы.
- Батч содержит события одного потока и курсор этого потока.
- `seek` с `latest` или `from_seqno` перематывает все потоки подписки,
  `after_cursor` — только поток этого курсора.

Разделять типы на разные подписки поэтому не нужно.

### Устройство курсора

- Непрозрачная строка. Сейчас кодирует `mc_seqno` последнего доставленного
  блока. Формат версионируется, чтобы при необходимости добавить позицию внутри
  блока.
- Курсор не строится на `lt`: между шардами `lt` не согласован с порядком
  финализации mc-блоков, и опрос по `lt > last` по нескольким адресам теряет
  транзакции.
- Батч содержит целые mc-блоки. Рядом с курсором отдаётся `position`
  (`mc_seqno`, `utime`) для отладки.
- Курсор кодирует только позицию, фильтр живёт в подписке. Курсор глобальный и
  не привязан к фильтру: один и тот же диапазон блоков с одним и тем же
  фильтром всегда даёт одни и те же события.
- Каждое событие несёт свой `mc_seqno`, поэтому курсор можно восстановить из
  последнего обработанного события.
- У батча есть лимит по байтам: приёмники ограничивают размер тела запроса.
  Если совпадения одного mc-блока не помещаются в лимит, понадобится позиция
  внутри блока — ради этого курсор и сделан непрозрачным. **Открыто:** значение
  лимита.

### Начальная точка

Задаётся явно при создании подписки и при перемотке (`seek`). Умолчания нет,
чтобы потеря курсора не превращалась в тихое продолжение с головы.

| Параметр | Смысл |
|---|---|
| `latest` | с текущего `head`, события со следующего блока |
| `start_seqno` | с mc-блока N включительно |
| `cursor` | продолжить после курсора (только `seek`) |

Перевода времени в mc-блок нет: seqno по времени клиент получает через v3 API.

Точка глубже доступной глубины — явная ошибка с самым ранним доступным
курсором в ответе.

Сценарий «текущее состояние плюс изменения»: сначала создать подписку с
`latest`, потом прочитать состояние через v3 API. Дыр нет, возможны дубли,
которые клиент отсеивает по идентификаторам событий.

## 5. Источник данных

### Граница готовности (`head`)

`ton-index-postgres` вставляет батчи не по порядку: более новый блок может
закоммититься раньше старого. Поэтому `head` — не `max(seqno)`.

- **`transactions`, `account_state_change`, `jettons_change`:**
  `_ton_indexer_progress.finalized_mc_seqno`. Граница двигается только подряд
  (`advance_ton_indexer_progress` останавливается на первой дыре), а батч
  вставки — одна транзакция Postgres: строка mc-блока видна вместе со всеми его
  данными.
- **`actions`:** минимум из границы индексера и непрерывной границы
  классификации. Сейчас классификатор отмечает блоки поштучно в
  `_blocks_classified`, сплошной границы нет. **Нужно добавить** функцию по
  образцу `advance_ton_indexer_progress`.
- Граница своя у каждого потока подписки (§4), поэтому отставание или
  остановка классификатора не задерживает поток транзакций.
- Actions отдаются только для трейсов в состоянии `complete`: actions
  соединяются с `traces` по `trace_id` и `mc_seqno_end` с условием
  `state = 'complete'`, так же как v3 отдаёт actions по `mc_seqno`. Проверено в
  `indexer/event_classifier.py`:
  - задача на блок классифицирует все трейсы с этим `mc_seqno_end`, включая
    незавершённые, поэтому без фильтра по состоянию в выдачу попали бы
    промежуточные actions растущего трейса;
  - трейсы больше 4 000 узлов не классифицируются, для них будут только события
    `transactions`;
  - упавшие трейсы попадают в `_classifier_failed_traces` и actions не имеют,
    но блок всё равно отмечается в `_blocks_classified`, поэтому граница
    классификации на них не застрянет;
  - повторная классификация старых блоков меняет actions задним числом; уже
    доставленные события повторно не отправляются.

### Правила чтения

1. Граница и данные читаются в одном снапшоте (`REPEATABLE READ`) и с одного
   узла. Граница с primary и данные с отстающей реплики дают пропуски.
2. Курсор никогда не уходит за `head`.
3. Полнота диапазона проверяется точно: в диапазоне из N номеров должно быть
   ровно N mc-блоков. Иначе курсор не двигается.
4. После failover с потерей хвоста граница может откатиться: индексер
   переиндексирует потерянный диапазон. Если курсор подписки выше `head`,
   доставка ждёт. Блоки финализированы, поэтому переиндексированные данные
   совпадут.

### Kvrocks

При включённом Kvrocks тела сообщений и текущее состояние лежат в нём. Kvrocks
пишется до транзакции Postgres, поэтому для блоков ниже `head` данные там уже
есть.

**Открыто:** если Kvrocks хранит только текущее состояние, то
`account_state_change` и `jettons_change` при догоне вернут последнее
состояние, а не состояние на тот блок. Семантику нужно зафиксировать.

### Сериализация и связь со схемой

Используются пакеты `ton-index-go` (`crud`, модели) — так уже делает
`ton-streaming-go`. JSON событий совпадает с v3 API.

Сервис зависит от внутренней схемы индексера (`_ton_indexer_progress`,
`_blocks_classified`, `_ton_hot_cold_split`), поэтому живёт в этом репозитории
и выпускается вместе с миграциями.

## 6. Hot и cold

**Решено:** в первой версии worker читает только hot. Подписка начинается и
догоняет только в пределах окна hot (недели), более раннюю историю клиент берёт
из v3 API.

- Самая ранняя доступная позиция — `_ton_hot_cold_split.seqno`. В установке без
  разделения hot/cold — первый проиндексированный блок.
- Курсор ниже этой границы переводит подписку в `expired` (§8).
- `head` берётся из hot.
- Проверка числа mc-блоков (§5) закрывает удалённую партицию в hot и
  устаревший кэш границы.

Если чтение из cold понадобится позже, известно, как его сделать:

- ось курсора совпадает с осью разделения hot/cold, поэтому батч целиком
  читается из одной базы и обрезается на `split − 1`, строки двух баз не
  сшиваются;
- проверка числа mc-блоков корректна и в cold: логическая репликация переносит
  транзакции целиком;
- `_blocks_classified` придётся добавить в публикацию `hot_to_cold_pub`;
- в cold нет партиций по seqno, а адресные индексы построены по `lt`, поэтому
  диапазон seqno переводится в диапазон `lt` с запасом и затем точно
  фильтруется по seqno.

## 7. Фильтры

Модель как в `eth_getLogs`: внутри измерения OR, между измерениями AND, пустое
измерение означает «любое значение». Одна подписка — одно правило.

| Тип события | Адрес совпал, если | Предикаты |
|---|---|---|
| `transactions` | транзакция исполнилась на адресе | opcode входящего сообщения |
| `actions` | адрес есть в `action.accounts` | `action_types` |
| `account_state_change` | это состояние адреса | — |
| `jettons_change` | адрес — jetton-кошелёк или его владелец | — |

В `action.accounts` входят аккаунты транзакций экшена, source, destination, их
jetton-кошельки и аккаунт инициирующей транзакции. Jetton master туда не
входит, поэтому фильтр по asset, если понадобится, будет отдельным измерением.

### Исполнение

1. **Маршрутизация:** обратный индекс «адрес → подписки».
2. **Предикаты:** opcode входящего сообщения, `action_types`.
3. **Проекция:** оставить только то, что касается подписки, и отрендерить
   actions под зафиксированные `supported_action_types`.

Переиспользуются `ton-streaming-go/v2/subscription_index.go` и
`AdjustForClient`. Чтение новых блоков и догон отличаются только стадией
выбора кандидатов. Стадии 2–3 — общий код, поэтому повторное чтение диапазона
даёт тот же результат.

### Правила детерминизма

- Фильтр строится только по неизменяемым полям события. Scam-флаги, address
  book и metadata — обогащение, а не критерии.
- `supported_action_types` фиксируется при создании подписки: `latest`
  меняется с релизами.
- Новый адрес гарантированно учитывается с блока `effective_from_seqno`,
  который возвращается клиенту. API вычисляет его как `head + 1`, прочитав
  `head` после коммита, а worker перед каждым блоком сверяет версии своих
  подписок; запас по времени не нужен ([subscriptions-api.md](subscriptions-api.md) §5).
- Это граница гарантии, а не фильтр. **Предложение:** при `seek` назад ко всему
  перечитываемому диапазону применяется текущий набор адресов. Иначе после
  пересинхронизации (§11) все адреса получат новую точку начала действия, и
  перемотка не доберёт пропущенное окно.

### Объём первой версии

Типы событий `transactions` и `actions`; `account_state_change` и
`jettons_change` — после того как будет решён открытый вопрос из §5. Фильтры:
адреса, opcode входящего сообщения для транзакций, `action_types` для actions.
Фильтры по `msg_body_hash` и asset не нужны. Подписки без адресов — по типу
или на весь поток — позже: для них нет адресного индекса, остаётся только
скан.

## 8. Доставка

```text
для каждой подписки, которой владеет экземпляр worker,
для каждого её потока, у которого есть данные и не идёт backoff:
    batch = read(stream, filter, after = cursor[stream])
    пустой батч → cursor[stream] = batch.cursor
    иначе       → POST через Smokescreen
                  2xx    → cursor[stream] = batch.cursor, сохранить
                  ошибка → backoff потока, повторить тот же батч
```

- В полёте не больше одного запроса на подписку. Потоки, у которых есть
  данные, отправляются по очереди. Поток в backoff не задерживает остальные.
- Повтор отправляет тот же батч с тем же `webhook-id`.
- Пустые батчи не отправляются. Курсор сохраняется периодически: откат курсора
  назад даёт только дубли.
- 2xx означает «обработал и сохранил». Таймаут короткий, долгую обработку
  клиент ставит в свою очередь.
- После N часов сплошных отказов любого потока вся подписка встаёт на паузу с
  сохранёнными курсорами; статусы описаны ниже.
- `seek` перематывает подписку. Через него работают восстановление, повторная
  доставка и пересинхронизация после восстановления хранилища (§11).

**Открыто:** таймаут, расписание ретраев, N часов до паузы.

### Статусы подписки (Решено)

| Статус | Доставка | Как попадает | Как выходит |
|---|---|---|---|
| `active` | идёт; при ошибках ретраи с backoff до потолка порядка часа | создание, `resume`, `seek` | — |
| `paused` | нет, курсор сохранён | клиент сам (`reason: manual`) или N часов сплошных отказов (`reason: endpoint_failing`) | `resume`: продолжает с курсора |
| флаг `suspended` | нет при любом статусе, курсор сохранён | административный API: отзыв ключа, конец тарифа | только административный API |
| `expired` | нет | курсор ниже самой ранней доступной позиции для этой подписки (§6) | только `seek` в доступную точку |

- `resume` продолжает с курсора, то есть с последнего подтверждённого батча, а
  не с момента паузы: клиент получает и период отказов.
- `expired` наступает не по таймеру, а когда курсор выпадает из окна hot. Это
  касается и активной подписки, которая догоняет медленнее, чем сдвигается
  окно.
- Из `expired` нет автоматического возврата. Дыра неизбежна, клиент признаёт её
  явным `seek` и добирает пропущенное через v3 API.
- Автопауза нужна не только ради экономии: за недели отказов домен может
  сменить владельца, и продолжать слать туда данные нельзя. После паузы без
  явного `resume` запросы не отправляются.
- О переходе в `paused` и заранее о приближении к `expired` нужно
  предупреждать. Через упавший endpoint этого не сделать, поэтому сервис
  отдаёт изменения статусов приватной стороне через административный API, а
  она уведомляет пользователя своими каналами.
- Подписка в `expired` хранится ещё M дней вместе с конфигом и адресами, потом
  удаляется. **Открыто:** M.

### Standard Webhooks

- `webhook-id` вычисляется детерминированно из подписки и тела запроса,
  поэтому стабилен между повторами и меняется, если изменилось содержимое.
- `webhook-timestamp` и `webhook-signature` вычисляются на каждую попытку:
  библиотеки проверки отбрасывают старые метки времени, поэтому подписанный
  запрос нельзя кэшировать между ретраями.
- Ротация секрета: на время ротации запрос подписывается старым и новым
  секретом, обе подписи идут в одном заголовке.
- Тело запроса: `type`, `timestamp`, `data`. Формат описан в
  [delivery-format.md](delivery-format.md).
- `410 Gone` ставит подписку на паузу с причиной `endpoint_gone`, `3xx`
  считается ошибкой, `Retry-After` учитывается — как требует Standard Webhooks.

### Smokescreen

- Все исходящие доставки идут через прокси. Он сам резолвит DNS и проверяет
  итоговый IP, это закрывает и DNS rebinding.
- Проверка URL при создании подписки нужна только для удобства: сразу отказать
  на очевидно внутреннем адресе. Защиту обеспечивает прокси.
- В open source прокси опционален. Без него обязательна встроенная проверка
  адреса перед соединением через `net.Dialer.Control`.

### Почему не готовый сервис доставки

Svix (MIT) и Hookdeck Outpost (Apache-2.0) — очереди отдельных сообщений:

- порядок по умолчанию не гарантирован;
- окно ретраев конечно;
- курсор двигался бы в момент приёма сообщения сервисом, а не клиентом;
- payload хранился бы второй раз.

Convoy (Elastic License 2.0) и Hook0 (SSPL) не подходят по лицензии.

- [Svix: FIFO ordered webhooks delivery](https://svix.com/blog/fifo-ordered-webhooks-delivery)
- [Svix: retry schedule](https://docs.svix.com/retries)
- [Hookdeck Outpost](https://hookdeck.com/docs/outpost/overview)

- [Standard Webhooks](https://www.standardwebhooks.com/)

```text
шлюз и кабинет (приватно) ──▶ subscriptions-api ──▶ БД подписок
                                                         ▲
                               webhook-worker ───────────┘
                                 ├──▶ hot Postgres
                                 ├──▶ Kvrocks
                                 └──▶ Smokescreen ──▶ URL клиентов
```

Новые процессы: `subscriptions-api` и `webhook-worker` из этого репозитория
(допустим один бинарник с флагом роли) и Smokescreen. Индексер, классификатор,
репликация hot→cold, v3 API и streaming v2 не меняются.

| Компонент | Куда ходит | Зачем |
|---|---|---|
| Шлюз и кабинет (приватные) | MongoDB | ключи, тарифы |
| | `subscriptions-api` | изменение подписок с владельцем и лимитами в заголовках; административные вызовы |
| `subscriptions-api` | БД подписок | запись с синхронным коммитом |
| | hot Postgres, только чтение | `head`: начало действия нового адреса, границы для `seek` |
| `webhook-worker` | БД подписок | аренды, курсоры, наборы адресов, изменения наборов |
| | hot Postgres, только чтение | новые блоки и догон; можно с реплики |
| | Kvrocks, только чтение | тела сообщений и текущие состояния |
| | Smokescreen | все исходящие доставки |
| Smokescreen | URL клиентов | только интернет |

### Worker

- Внутренней шины между чтением блоков и доставкой нет. Каждый экземпляр
  арендует часть подписок, сам читает новые блоки из hot и раздаёт их своим
  подпискам. Блок читается один раз на экземпляр.
- При отказе экземпляра его аренды истекают, подписки забирают остальные
  экземпляры и продолжают с сохранённых курсоров.
- Подписки распределяются по весу, а не по количеству: подписка на миллион
  адресов занимает сотни мегабайт памяти.
- Изменения наборов адресов приходят из БД подписок через уведомление плюс
  периодический опрос по версии: уведомления теряются при разрыве соединения.

### Сетевые правила

- Worker и API видят внутреннюю сеть, выхода в интернет у них нет.
- Smokescreen выходит в интернет, внутренняя сеть закрыта ему на уровне
  файрвола, а не только его собственным списком запретов.
- В MongoDB из открытой части не ходит никто.

## 10. Граница open source и приватной части

Зависимости идут только от приватного сервиса к открытому. Открытый сервис не
знает, что такое пользователь, тариф или ключ.

- **Владелец** — идентификатор аккаунта из заголовка `X-Owner-Id`, который
  выставляет HAProxy (Решено). Аккаунт, а не API-ключ: подписки переживают
  ротацию ключа. `X-Limiting-Key` сервис не читает.
- **Лимиты на запрос** приходят заголовками `X-Max-Webhook-Subscriptions` и
  `X-Max-Webhook-Addresses`. Открытый сервис сравнивает их с текущим числом
  подписок и адресов владельца. Хранимых лимитов владельца пока нет (Решено).
- **HAProxy вырезает** эти заголовки из входящих запросов клиентов.
- **Административный API** нужен потому, что подписка живёт дольше запроса:
  - приостановить или удалить все подписки владельца (отзыв ключа, конец
    тарифа);
  - отдать учёт доставок для биллинга.
- **Кабинет** вызывает тот же API, что и бэкенды клиентов. Данных подписок в
  MongoDB нет — источник истины один.
- **Режим без шлюза** для тех, кто разворачивает сервис у себя: один владелец
  по умолчанию.
- Сервис доверяет заголовкам и административному API, поэтому доступен только
  из приватной сети.

## 11. Хранилище подписок

| Данные | Объём | Что будет при потере | Требование |
|---|---|---|---|
| Конфиг подписки: фильтр, URL, секрет | мало | клиент пересоздаёт подписку | бэкап |
| Набор адресов | до миллионов строк на подписку | клиент молча не получает события по потерянным адресам | синхронная запись до ответа клиенту |
| Курсор доставки | одно значение на подписку | откат назад даёт только дубли | можно сохранять изредка |
| Состояние ретраев, журнал доставок | растёт, с TTL | ничего страшного | бэкап не нужен |

### Модель набора адресов

- Одна строка на пару (подписка, адрес). Повторное добавление идемпотентно.
- Источник истины по адресам у клиента: после смены эпохи он заново добавляет
  весь набор и перематывает подписку
  ([subscriptions-api.md](subscriptions-api.md) §4.3).

### Размещение (Предложение)

Отдельная база в hot Patroni-кластере. Условия:

1. В общей конфигурации кластера `synchronous_commit = local`, чтобы индексер,
   классификатор и ручные сессии вели себя как сейчас.
2. Роли сервиса `synchronous_commit = on`. Транзакции, меняющие наборы
   адресов, дополнительно выставляют `SET LOCAL synchronous_commit = on`, чтобы
   гарантия не зависела от настройки ролей в конкретной установке.
3. Включить `synchronous_mode` в Patroni.
4. Бэкап этой базы через `pg_dump` по расписанию.
5. Процедуры, пересоздающие hot-кластер, должны переносить эту базу.
6. У сервиса свой DSN и ни одного запроса, соединяющего его таблицы с
   таблицами индексера. Тогда вынос в отдельный кластер — это дамп,
   восстановление и смена строки подключения.

Побочный эффект синхронного коммита: WAL у кластера общий, поэтому запись
подписки ждёт, пока реплика получит и весь WAL индексера перед ней. Задержка
добавления адреса зависит от отставания реплики.

**Открыто:** в конфиге Patroni из репозитория репликация асинхронная
(`maximum_lag_on_failover`, нет `synchronous_mode`), потеря хвоста при failover
для индексера — штатная ситуация. Как настроен продовый hot-кластер и можно ли
включить синхронный режим, нужно проверить.

### Эпоха хранилища

Даже синхронная реплика не защищает от ошибки оператора или логической порчи
данных, после которых придётся восстанавливаться из бэкапа.

- После восстановления из бэкапа номер эпохи увеличивается. Он приходит в
  каждой доставке и каждом ответе API.
- Клиент, увидев новую эпоху, заново добавляет весь набор адресов и
  перематывает подписку на момент бэкапа. Лог воспроизводим, поэтому пропущенное окно
  добирается, а дубли отсеиваются.
- Запасной вариант без синхронной реплики: сервис замечает failover по смене
  timeline Postgres и увеличивает эпоху.

## 12. Вне рамок первой версии

- Публичная ручка чтения событий — не планируется.
- События pending и confirmed — streaming v2.
- Подписки без адресов: по типу, на весь поток.
- Тип события `trace` с полным деревом трейса.
- Доставка в очереди клиента (Kafka, SQS).
- Начало и догон глубже окна hot: чтение из cold (§6).
- Фильтры по asset и по `msg_body_hash`.

## 13. Порядок работ

1. Индексер: непрерывная граница классификации.
2. Библиотека чтения батча: `head`, проверка полноты, фильтры, сериализация.
3. Хранилище подписок, `subscriptions-api`, административный API.
4. `webhook-worker`: аренды, чтение новых блоков, догон, доставка через
   Standard Webhooks и Smokescreen.

## 14. Открытые вопросы

- Продовая конфигурация hot Patroni-кластера и возможность включить
  синхронный режим (§11).
- Семантика `account_state_change` и `jettons_change` при догоне (§5).
- Числа: лимит батча в байтах, таймаут, расписание ретраев, время до паузы,
  срок хранения подписок в статусе `expired`.
- Распределение подписок по экземплярам worker с учётом веса.
