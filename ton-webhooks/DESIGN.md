# ton-webhooks: дизайн v1

Статус: согласованный объём v1, 2026-10-27; документ описывает целевую
реализацию. API и схема состояния — в [subscriptions-api.md](subscriptions-api.md),
HTTP-контракт — в [delivery-format.md](delivery-format.md).

## 1. Задача и объём

Клиент задаёт адреса и фильтры и получает finalized-события TON с полным
payload из `ton-index-go`. Сервис доставляет события повторно до подтверждения
либо явно останавливает подписку; молчаливого перехода на текущую голову нет.

В v1 два типа подписок: `transactions` и `jetton_transfers`. Одна подписка —
один неизменяемый тип, один URL, один набор адресов, один курсор и не более
одного текущего неподтверждённого HTTP-батча. Для двух типов создаются две
подписки. Движок чтения и доставки общий; порядка между подписками нет.

Источники — hot Postgres индексера и, когда включён, Kvrocks. Общего отдельного
лога всех событий и архива всех доставленных payload нет. Полное тело
неподтверждённого батча сохраняется в БД подписок до первой отправки.

Полные тела сообщений и account state входят в payload. Address book и
metadata в v1 отсутствуют. Общие actions, `seek`, отдельный replay API и
`stop_at_seqno` отложены. Для проверки endpoint есть подписанный `test`.

## 2. Гарантии

| Свойство | Контракт |
|---|---|
| Финальность | Только finalized-транзакции; для jetton — finalized-транзакция получения |
| Доставка | At-least-once в пределах доступности исходных данных и сохранённого pending batch |
| Подтверждение | `2xx` означает, что клиент надёжно принял батч, в том числе в свою долговечную очередь |
| Повтор | Те же байты тела и тот же `webhook-id`; timestamp заголовка и подпись новые |
| Порядок | Следующий диапазон не отправляется до подтверждения текущего; запоздавшие повторы возможны |
| Недоступность данных | Ожидание или явная остановка, без выдачи неполного события как полного |
| Истечение истории | `expired`, без автоматического пропуска потерянного диапазона |
| Задержка | Цель — единицы секунд после финализации при нормальной работе; SLA после измерений |

Клиент дедуплицирует события по `events[].id`. Удаление подписки — явная
отмена дальнейшей доставки, включая сохранённые данные.

Порядок означает порядок продвижения сервиса, а не отсутствие параллельной
обработки на endpoint: HTTP-таймаут не отменяет обработку клиента, а прежний
worker может отправить запоздавший запрос после потери аренды. Клиент,
которому важен порядок обработки, сериализует свою очередь и удаляет дубли.

Полнота относится к описанному набору событий и поддерживаемым jetton-wallets.
Поток jetton включает распознанные индексером переводы из `jetton_transfers`
с подтверждённым получением (§5.2). Не обещаем распознавать произвольную
логику кастомного токена по одному opcode.

## 3. События и фильтры

| Подписка | Событие | Адрес совпал, если | Дополнительные фильтры |
|---|---|---|---|
| `transactions` | `transaction` | `transaction.account` входит в набор | `in_msg_opcodes` |
| `jetton_transfers` | `jetton_transfer` | владелец отправителя/получателя входит в набор с учётом направления | `direction`, `jetton_masters` |

Внутри списка значений OR, между измерениями AND. Пустые списки opcode или
masters не ограничивают результат. Пустой набор адресов не совпадает ни с
одним событием; подписки на всю сеть в v1 нет. Активная подписка с пустым
набором может продвигаться по пустым диапазонам. Для первоначальной настройки
она создаётся на паузе.

`transactions` включает успешные и неуспешные транзакции. `jetton_transfers`
включает только подтверждённое зачисление между кошельками поддерживаемого
jetton, в том числе внутри DEX swap. Mint, burn, неудачные запросы перевода и
общие actions не входят в этот поток.

`direction` принимает `incoming`, `outgoing`, `both` (по умолчанию `both`).
Направление определяется относительно каждого адреса подписки: incoming —
совпал получатель, outgoing — отправитель. При совпадении обоих или при
переводе себе событие приходит один раз, `matched_addresses` содержит
уникальные совпавшие адреса. Адреса jetton-wallet и master не становятся
адресами владельца; master — отдельный фильтр `jetton_masters`.

Фильтры не зависят от metadata, scam-меток и текущего баланса. Маршрутизация
использует обратный индекс «адрес → подписки». Чтение текущих блоков и догон
используют одинаковые правила распознавания, фильтрации и сборки.

## 4. Курсор и начальная позиция

Непрозрачный версионированный курсор содержит сеть, тип подписки, `mc_seqno`
и либо признак полностью обработанного блока, либо ключ последнего события
внутри блока. Внутриблочная позиция поддерживается с первого релиза.

| Поток | Порядок |
|---|---|
| `transactions` | `(mc_block_seqno, lt, transaction_hash)` |
| `jetton_transfers` | `(receiver_mc_block_seqno, receiver_lt, receiver_transaction_hash)` |

Хеши сравниваются по байтам, не по base64-строке. Принимающая транзакция имеет
одно входящее сообщение, поэтому одному подтверждённому переводу соответствует
один ключ. Порядок только по `lt` между шардами не используется.

`cursor` — последняя полностью обработанная позиция; для батча диапазон
`(from_cursor, cursor]`. Пустые диапазоны тоже продвигают курсор, но без HTTP.
По номеру блока отдельного события восстановить точный курсор нельзя.

В штатном режиме накопленный прогресс по пустым диапазонам сохраняется
каждые 30 секунд либо покрывается следующим сохранённым батчем. При сбоях
отставание может быть больше. Worker различает сохранённый `cursor` и
`scan_cursor` в памяти. Проверка CAS и `from_cursor` нового батча опираются
на сохранённый `cursor`: ещё не сохранённый пустой префикс входит в интервал
батча, а cursor доставки продвигается после ACK. Если батча нет, периодический
checkpoint продвигает cursor без HTTP с теми же проверками состояния.

Границей изменений конфигурации (§7) служит сохранённый курсор. Прогресс в
памяти привязан к исходному cursor, `config_version` и
`lease_token`; при их несовпадении worker отбрасывает его и перечитывает
состояние. После падения несохранённые пустые диапазоны сканируются заново;
это само по себе не создаёт повторных доставок.

Начальная точка задаётся обязательным полем `start_mc_seqno`:

- `"start_mc_seqno": "latest"` — начать с `head + 1`, после текущей границы готовности;
- `"start_mc_seqno": N` — целый номер masterchain-блока N включительно.

При создании `"latest"` однократно разрешается в конкретный номер. В подписке
сохраняется только этот номер; во всех ответах `start_mc_seqno` — число.
Идемпотентный повтор create возвращает прежний результат. При `resume`
начальная позиция не пересчитывается. Допустим диапазон
`earliest_mc_seqno … head + 1`.
Подписка создаётся `paused/manual`: клиент получает секрет, загружает адреса,
проверяет endpoint и вызывает `resume`.

`seek` и изменение `start_mc_seqno` отсутствуют. Для повторного чтения создаётся
новая подписка с числовым `start_mc_seqno`; она не меняет live-подписку. Клиент сам выбирает
перекрытие и дедуплицирует события. История старше hot доступна через v3 API.

Согласованный «снимок состояния + изменения» не является гарантией v1.
Обычного запроса текущего состояния после создания подписки недостаточно:
для такого протокола нужны позиция и свежесть снимка.

## 5. Источники и подтверждение jetton

### 5.1. Граница готовности

Postgres индексера коммитит батчи не по порядку. Используется непрерывная
граница `_ton_indexer_progress.finalized_mc_seqno`, а не `max(seqno)`.
Граница, блоки и строки событий читаются с одного узла в `REPEATABLE READ`.
Проверяется наличие всех mc-блоков сканируемого диапазона.

При включённом Kvrocks:

```text
head = min(Postgres.finalized_mc_seqno, watermark выбранного узла Kvrocks)
```

Граница Kvrocks — `ton-index:v1:progress:finalized_mc_seqno` из его собственного
потока репликации. Запись Kvrocks перед Postgres не заменяет эту проверку:
независимый failover может откатить только одно хранилище. Чтение закрепляется
за проверенным узлом; при его смене готовность проверяется заново. Нет ключа
watermark — источник не готов, а не «готов до головы».

Общей транзакции Postgres/Kvrocks нет. Поэтому кроме границ проверяется
наличие всех обязательных объектов, читаемых по неизменяемым хешам. Откат
`head` ниже курсора вызывает ожидание, но не перемотку. Сохранённый pending
batch можно доставлять без доступа к индексеру.

### 5.2. Подтверждённый jetton transfer

Источник исходного запроса — существующая таблица `jetton_transfers`,
независимая от таблицы `actions`. Наличие записи и `tx_aborted=false`
подтверждает только отправляющую транзакцию, не получение.

Worker сканирует входящие сообщения `internal_transfer` (`0x178d4519`) по
позиции принимающей транзакции и восстанавливает связь:

```text
принимающая transaction + входящее message
    → исходящее message с тем же msg_hash
    → отправляющая transaction
    → jetton_transfers по tx_hash, tx_lt и mc_seqno отправителя
```

Проверки для поддерживаемого обычного перевода:

1. Исходная запись и отправляющая транзакция не aborted. Исходящее сообщение
   принадлежит именно этой транзакции, source совпадает с её jetton-wallet.
2. Входящее сообщение принимающей транзакции имеет тот же `msg_hash`, не
   bounced и корректное тело `internal_transfer`. `query_id` не ключ связи.
3. Принимающий аккаунт — подтверждённый jetton-wallet нужного master и owner,
   соответствующего `jetton_transfers.destination`. Переиспользуется проверка
   индексера через `get_wallet_address(owner)` master-контракта.
4. Принимающая транзакция не aborted, compute успешен, action phase, если
   присутствует, успешна. Транзакция находится не выше `head`.
5. Сумма зачисления берётся из `internal_transfer`; запрошенная сумма остаётся
   в исходном объекте `JettonTransfer` без изменения его семантики.

Для проверки принадлежности кошелька используются данные, соответствующие
поддерживаемой реализации на момент события. Одного текущего заявленного
`owner/master` произвольного контракта недостаточно. Набор поддерживаемых
реализаций и границы распознавания фиксируются при реализации и тестировании.

Отправляющая и принимающая транзакции могут находиться в разных mc-блоках.
Наличие sender без receiver ещё не создаёт кандидата на зачисление. Worker
продолжает обход блоков по позиции receiver и не держит курсор на блоке sender:

| Доступные данные | Действие |
|---|---|
| Блок 100: sender и запись `jetton_transfers`; receiver ещё нет | Не отправлять событие; обработать остальные события и продвигаться дальше |
| Блоки 101–102: receiver ещё нет | Продолжать обычное чтение; отсутствие receiver не ошибка источника |
| Блок 103: receiver появился, но `head < 103` | Дождаться готовности блока 103, не выдавать предварительное событие |
| `head >= 103`, receiver и контекст готовы | Связать receiver с sender из блока 100 по сообщению, проверить зачисление и выдать событие с позицией блока 103 |

Это работает и при получении в следующем блоке, и позже; фиксированного
ожидания «один блок» нет. Отдельная очередь ожидающих sender не нужна,
обновления старой строки `jetton_transfers` для запуска доставки тоже не
требуется. Связь с sender ищется в более ранних доступных блоках, не только
в текущем диапазоне receiver. Для `direction=outgoing` действует тот же
порядок: после проверки receiver событие маршрутизируется также по owner
отправителя. Если успешного получения не произошло, события зачисления нет.

Не ждём завершения trace, распознавания swap, `excesses` или
`transfer_notification`; последнего может не быть при нулевом
`forward_ton_amount`. Успех дальнейшей операции получателя не входит в
гарантию зачисления.

После обнаружения receiver различаются три случая:

- Источник ещё не готов или ожидаемый sender, сообщение, тело либо проверочный
  контекст временно недоступны: не продвигаться за затронутого кандидата,
  выставить `blocked_reason=source_not_ready` и повторить чтение.
- Готовность источника проверена, sender найден, но для него нет распознанной
  записи `jetton_transfers`: исключить кандидата как `unrecognized_transfer`
  и учесть причину в метриках. Это граница распознавания потока, не пауза
  подписки. Отсутствие самого sender, сообщения, обязательного тела или
  проверочного контекста не подпадает под это исключение.
- Установлена потеря необходимого контекста: `paused/source_data_unavailable`.
  Sender может оказаться старше hot, хотя принимающий блок ещё доступен.

Доказанные mint, неуспешные переводы и неподдерживаемые форматы также
исключаются по правилам распознавания, а не выдаются как успешные переводы
с неполными данными. Срок доступности контекста sender ограничивает догон;
ожидание готовности не восстанавливает уже удалённые данные.

## 6. Полный payload

Используются общие модели и сериализация `ton-index-go`; отдельного
сокращённого transaction DTO нет. Поля `Transaction`, включая description,
in/out messages, message content, init state и account state before/after,
передаются в семантике v3. Для jetton передаются полный `JettonTransfer`,
обе полные транзакции и объект `receipt` из delivery-format.md §3.2.

Account state загружается по `account_state_hash_before/after`. Последнее
состояние аккаунта не подставляется вместо исторического. Текущий индексер
не сохраняет все промежуточные состояния внутри блока; как в v3, тогда
объект содержит хеш, а остальные поля могут быть незаполненными. Это не
обещание исторических code/data BOC для каждой транзакции.

Допустимое отсутствие state отличается от временного отсутствия обязательного
тела сообщения. Для ожидаемого тела, в том числе пустой ячейки с известным
хешем, cache miss не превращается в успешный неполный payload. Общий CRUD
дополняется проверкой полноты; само отсутствие ошибки запроса недостаточно.
Address book и metadata не загружаются, их полей и переключателей в v1 нет.

Точное представление фиксируется при сохранении батча. Retry не вызывает
рендеринг повторно. Новая подписка, читающая ту же историю после обновления
декодеров, может получить иной набор производных полей с тем же ID события;
это не механизм доставки исправлений.

## 7. Изменения конфигурации

Адреса, фильтры, URL и лимиты батча меняются только в `paused`;
описание — в любом состоянии. PATCH адресов в active или expired — `409`.
Тип подписки и начальная позиция неизменяемы.

Изменения фильтров и адресов возвращают точную границу `effective_after_cursor`:

- pending batch есть — после его `to_cursor`;
- pending нет — после сохранённого курсора, без прогресса только в памяти.

Сохранённые события, включая `matched_addresses`, не меняются. Удалённый
адрес ещё может встретиться в них. При догоне новый фильтр применяется и к
историческим событиям после указанной позиции. Первоначальная загрузка
адресов на паузе применяется от зафиксированного старта.

API блокирует строку подписки, меняет конфигурацию, увеличивает
`config_version` и фиксирует границу в одной транзакции. Worker читает
согласованные фильтры и набор, а перед сохранением батча сравнивает версию,
владельца/token аренды и исходный курсор. То же сравнение обязательно
для продвижения по пустому диапазону. Конкурирующее изменение заставляет
пересобрать ещё не сохранённый результат.

Перед новой выборкой worker сверяет `config_version` с БД. При получении
аренды, отсутствии снимка или несовпадении версии он загружает полный
согласованный снимок адресов, фильтров и `config_version`. Журнала дельт нет.
После resume изменения применяются к следующей выборке; если конфигурация
не менялась, повторная загрузка того же набора не нужна.
Сохранённый pending можно отправить до загрузки набора: его отбор уже
зафиксирован. Старый снимок не используется для нового сканирования после
изменений; продление аренды не доказывает актуальность кэша. Проверки версии
сохраняются, в том числе для scan, начатого до pause и завершившегося после resume.

Реальная смена URL в той же транзакции увеличивает `lease_token` и отзывает
аренду: worker_id и lease_until становятся NULL. Pending, его байты и
`webhook-id` сохраняются. Ответ прежней попытки не применяется из-за старого
token, даже при последовательности URL A → B → A. После `resume` нужен новый
claim; параметры endpoint перечитываются из БД вместе с проверкой аренды при
резервировании попытки. Старый URL из кэша не переносится в новую аренду.
Изменение адресов/фильтров и обычный pause не отзывают уже начатую попытку:
её актуальный ACK может подтвердить неизменный pending. Уже ушедший HTTP-запрос
физически отозвать нельзя.

## 8. Доставка и состояния

### 8.1. Цикл worker

```text
проверить active, отсутствие suspended и действующую аренду
если pending batch есть:
    использовать сохранённые байты
иначе:
    прочитать диапазон и проверить готовность, полноту и фильтр
    если событий нет: продвинуть позицию в памяти; сохранять лениво (§4)
    иначе: под блокировкой повторно проверить состояние,
           config_version/worker_id/lease_token/cursor и срок аренды
           и сохранить тело, webhook-id и границы до HTTP

если есть pending:
    под блокировкой повторно проверить разрешение доставки и аренду,
    прочитать текущие URL/секреты, зарезервировать попытку и commit
    отправить сохранённые байты

после 2xx:
    проверить владельца, актуальный lease_token/webhook-id и срок аренды
    одной транзакцией продвинуть cursor, удалить pending batch,
    записать batch_acked в общий outbox
после ошибки:
    с теми же проверками сохранить результат и расписание повторов
```

Транзакция БД не удерживается во время HTTP. `lease_token` монотонно растёт
при новом claim и принудительном отзыве аренды при смене URL;
`config_version` защищает сборку по фильтрам. Одного сравнения курсоров
недостаточно. Старые ответы не меняют состояние, даже если диапазон совпал.
Claim, отзыв аренды, фиксация сканирования, PATCH и ACK сериализуются строкой подписки.

Диспетчер запускает не более одной текущей попытки на подписку. Проверка
срока аренды перед отправкой обязательна, но не исключает запоздавший запрос
старого worker. После падения между приёмом клиентом и сохранением ACK
отправляется тот же батч повторно.

Аренды продлеваются ограниченными пачками с ограниченным временем ожидания
блокировок. Каждый UPDATE проверяет worker_id, ожидаемый lease_token и
неистёкший срок; через RETURNING worker проверяет, какие аренды продлены.
Истёкшая или сменившая владельца аренда не продлевается: нужен новый claim.
Неудача одной пачки не задерживает продление всех подписок worker; отправка
без действующей аренды запрещена.

Периодическое сохранение пустых диапазонов тоже выполняется ограниченными
пачками с проверками active/suspend, cursor, версии и аренды.
Блокировки берутся в общем порядке owner → subscription → lease, пропуская
ненужные уровни; внутри уровня — по ID. Это сокращает число синхронных
коммитов без одного неограниченного запроса на все подписки.

### 8.2. Повторы

- HTTP-таймаут — 15 секунд, редиректы запрещены.
- Задержки после последовательных отказов: 5 секунд, 30 секунд, 2 минуты,
  10 минут, затем 1 час. Jitter — коэффициент от 0.8 до 1.2.
- Для `429`, `502`, `503`, `504` учитывается корректный `Retry-After`.
  Подсказка ограничивается диапазоном 0…1 час; итоговая задержка — максимум
  расписания с jitter и ограниченной подсказки.
- После 24 часов непрерывных отказов — `paused/endpoint_failing`. Пауза
  наступает по дедлайну, а не только после следующего HTTP-ответа.
- `410` — сразу `paused/endpoint_gone`; `413` — `paused/payload_too_large`.
- Остальные не-2xx, DNS/TLS/connection errors и таймауты повторяются по расписанию.
- `failing_since` сбрасывается после ACK или явного перехода paused → active.
  При resume сбрасывается и consecutive_failures, но не общий attempt батча.
  Повторный `resume` уже active-подписки не сбрасывает дедлайн.

### 8.3. Размер и ответ 413

По умолчанию до 500 событий и целевые 1 MiB (1 048 576 байт) сериализованного
JSON с оболочкой. Блок можно разделить. Одиночное событие сверх целевого
размера отправляется целиком отдельным батчем; усечения и замены ссылкой нет.

После `413` подписка ставится на паузу, pending сохраняется без изменения.
Клиент увеличивает лимит endpoint либо на паузе меняет URL на приёмник,
способный принять весь батч, затем вызывает `resume`. Повтор содержит те же
байты и webhook-id. Ни автоматического, ни ручного разделения уже сохранённого
батча в v1 нет.

PATCH лимитов влияет только на будущие батчи и не разблокирует слишком
большой pending. Его нельзя пропустить и перейти к следующему диапазону.
Если текущий endpoint имеет неизменяемый меньший лимит, для продолжения
этой подписки нужен другой приёмник. Это относится и к одиночному большому
событию; полные тела и account state не сокращаются.

### 8.4. Статусы

| Состояние | Поведение |
|---|---|
| `paused/manual` | начальная настройка или ручная пауза; без новых попыток |
| `active` | чтение, отправка и retry; временное ожидание источника видно в `blocked_reason` |
| `paused/endpoint_failing` | 24 часа отказов |
| `paused/endpoint_gone` | получен `410` |
| `paused/payload_too_large` | получен `413` |
| `paused/source_data_unavailable` | установлена потеря необходимых исходных данных |
| `expired/history_unavailable` | следующий незаготовленный диапазон вышел из hot |
| `suspended=true` | административный запрет поверх любого статуса |

`pause` не отменяет уже начатую попытку: её актуальный ACK может сохранить
прогресс. `resume` продолжает pending batch, затем чтение от курсора.
Сам по себе resume ничего не пропускает. Статус `expired`
не возобновляется: клиент восстанавливает историю через v3 и создаёт новую
подписку с явной точкой. Автоматического удаления expired-подписок в v1 нет;
удаление делает клиент или администратор.

Все изменения статуса и существенные изменения блокировки источника
попадают в транзакционный outbox. Предупреждение `retention_at_risk`
создаётся также для active/paused-подписок, приближающихся к границе hot.

## 9. Компоненты и безопасность

```text
шлюз/кабинет (приватно) → subscriptions-api → БД подписок
                               ↓                 ↑
                        общая библиотека ← webhook-worker
                               ↓                 ↓
                        hot Postgres/Kvrocks   Smokescreen → endpoint
```

`subscriptions-api` и `webhook-worker` — процессы этого репозитория, допустим
один бинарник с ролями. Общая библиотека читает блоки, проверяет jetton и
собирает payload. Классификатор actions для v1 не нужен. Переиспользуются
модели `ton-index-go` и подход к индексу адресов из streaming v2.

Workers ограниченными пачками забирают свободные или истёкшие аренды
допустимых к обработке подписок и удерживают их, пока обслуживают подписки.
Для worker задаются лимиты числа аренд и параллельных операций.
Здоровые workers не перемещают подписки между собой ради выравнивания нагрузки;
после освобождения или истечения аренды её может забрать другой worker.
Число workers и лимиты меняет оператор по измерениям.
Worker совместно читает новые блоки для своих подписок, а догон выполняет
с отдельными бюджетами, чтобы он не вытеснял live-доставку.
Поддержку миллионов адресов подтверждаем измерениями, не только архитектурой.

Все исходящие доставки и test идут через Smokescreen. Он проверяет фактический
IP при соединении; редиректы не выполняются. Worker/API не имеют прямого
выхода в интернет, прокси не имеет доступа во внутреннюю сеть на уровне
файрвола. Для самостоятельной установки без прокси обязательна эквивалентная
проверка адреса при каждом соединении, включая DNS rebinding.

Подписи — [Standard Webhooks](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md):
HMAC-SHA256, новый timestamp на попытку, неизменные тело и ID. Секреты
зашифрованы в БД, в течение 24 часов ротации подпись двойная. Повторная
ротация до конца этого периода запрещена.

## 10. БД подписок и приватная часть

Отдельная PostgreSQL-база со своим DSN, первоначально в hot Patroni-кластере.
Между таблицами подписок и индексера нет SQL join. Перенос в отдельный
кластер не меняет протокол.

Конфигурация, адреса, аренды, курсоры, pending payload, ретраи,
идемпотентные результаты, outbox и учёт ACK коммитятся с одинаковой
долговечностью: `synchronous_commit=on`. В HA-развёртывании нужны
`synchronous_mode` и `synchronous_mode_strict` Patroni с синхронной репликой;
без неё сервис не должен подтверждать запись как сохранённую на двух узлах.

Порядок включения обязателен. Значение `synchronous_commit` по умолчанию —
`on`, поэтому сначала в общей конфигурации кластера выставляется
`synchronous_commit=local`, а `on` задаётся только роли сервиса. Только после
этого включается `synchronous_mode`. В обратном порядке синхронными станут
индексер, классификатор и ручные сессии, а в strict-режиме они остановятся при
падении реплики. Цена strict-режима для самого сервиса: недоступность
синхронной реплики блокирует коммиты сервиса, необходимые перед новыми
HTTP-попытками; уже начатые запросы физически не отзываются.
До приёма трафика проверяются реальные подключения всех ролей через
`SHOW synchronous_commit`, включая переопределения роли, БД и сессии.
Pools пересоздаются, если изменённые настройки роли требуют новых соединений.
Проверка повторяется после failover; одной записи default в конфигурации мало.
Общий WAL влияет на задержку коммита, это требуется измерить. Бэкап включает
всю БД сервиса.

Владелец — аккаунт из `X-Owner-Id`, а не API-ключ. HAProxy удаляет клиентские
служебные заголовки и выставляет владельца и текущие квоты. Конкурирующие
проверки квот и suspend/create сериализуются блокировкой владельца.
Хранимых тарифных лимитов нет; есть состояние административной приостановки.
В режиме без шлюза используется владелец по умолчанию.

Единый durable outbox содержит управляющие события и `batch_acked` — учёт
принятого батча. У каждого события свой ID; `batch_acked` дополнительно
уникален по `webhook-id` и записывается в транзакции ACK с owner, subscription,
network, stream, числом событий, байт и временем принятия. Повтор HTTP или
stale ACK не создаёт повторного учёта. Записи переживают удаление подписки.

Приватная часть использует один логический потребитель общего claim/ACK
протокола: сначала надёжно сохраняет событие в своём входящем журнале с
дедупликацией по ID, затем подтверждает экспорт. Учёт и уведомления
обрабатываются из принятого журнала; независимые обработчики не конкурируют
за разные части исходного outbox. Учёт на приватной стороне также
дедуплицируется по webhook-id, тарифную интерпретацию определяет она.
Опрос по времени или максимальному ID не заменяет этот протокол.
До ACK экспорта TTL нет; подтверждённые записи можно удалить через 7 дней.
Отставание управляющих событий и batch_acked измеряется раздельно.

Диагностический журнал попыток хранится 7 дней; он не источник биллинга.

## 11. Hot, потеря данных и восстановление

`earliest_mc_seqno` — `_ton_hot_cold_split.seqno`, а без split — начало
доступного непрерывного диапазона индексера. Проверяется следующая нужная
позиция: после полностью обработанного N нужен N+1; внутри N нужен ещё N.
Курсор конца блока `earliest - 1` допустим.

Полный pending batch можно доставить после удаления исходных блоков из hot.
Пока он есть, его не удаляем и не объявляем истечение только из-за исходного
курсора. Доступность следующего незаготовленного
диапазона проверяем после его ACK; о риске предупреждаем заранее. На паузе
сохранённые данные не имеют автоматического TTL.

Потеря необходимых данных для jetton-связи, хотя принимающий блок ещё в hot,
обрабатывается явно по §5.2. Не выполняем скрытое чтение cold. Для выбора
`start_mc_seqno` в новой подписке API возвращает текущие границы, но не обещает
наличие более старого контекста каждого принимающего сообщения.

Восстановление из бэкапа требует режима остановки доставки на уровне
развёртывания, заданного вне восстанавливаемой БД. До запуска worker сверяем
подписки, адреса, URL, секреты, удаления и suspend с приватной стороной и
клиентами. Отдельным каналом сообщаем об инциденте, включая полностью
потерянные подписки. Уже доставленные данные могут повториться.

Числовой `epoch` и автоматическая клиентская пересинхронизация в v1 отсутствуют.
Нельзя просто восстановить старый URL/секрет и автоматически возобновить
доставку. Если согласованное продолжение невозможно, создаётся новая подписка
с явно выбранной позицией; недоступная история восстанавливается через v3.

## 12. За пределами v1

- Общий поток actions, traces, отдельные события изменения баланса/state.
- Pending/confirmed-события: они остаются в streaming v2.
- `seek`, отдельный replay API, `stop_at_seqno`, чтение cold worker-ом.
- `repack`: разделение или пересборка уже сохранённого pending batch.
- Публичный `preview`, изменение адресов вне paused и адаптивное
  перераспределение подписок между workers.
- Подписки на всю сеть без адресного фильтра, пользовательский код фильтров,
  фильтр по сумме.
- Address book, metadata и фильтры по ним.
- Доставка в Kafka/SQS и общий архив успешных payload.
- Гарантированное хранение каждого промежуточного account state и его BOC.

## 13. Реализация и проверки

Подробные этапы, зависимости и изменения существующих компонентов описаны
в [IMPLEMENTATION.md](IMPLEMENTATION.md).

1. Общая библиотека чтения: непрерывные границы, полнота payload, курсоры,
   подтверждение jetton через сообщения и фильтры.
2. БД сервиса и API: paused-create, наборы адресов, точные границы изменений,
   идемпотентность, общий outbox с учётом ACK и административное управление.
3. Worker: fencing аренды, сохранение до HTTP, ACK, retry и pause.
4. Проверки сбоев: падение до/после HTTP и ACK; поздний ответ прежнего worker;
   отдельный failover Kvrocks; pause/PATCH/resume при незавершённом scan;
   отправка и получение jetton в разных блоках; отсутствие notification;
   перевод внутри swap; потеря контекста отправителя; большой одиночный
   payload; доставка pending после выхода исходного диапазона из hot; восстановление
   бэкапа без отправок на устаревший URL.
5. Нагрузочные измерения: миллион адресов, совместное чтение блоков, тяжёлые
   payload, догон, объём pending-хранилища и задержки синхронного коммита.

До запуска уточняются продовая конфигурация Patroni, список поддерживаемых
jetton-wallets, индексы и стоимость join по сообщениям, ресурсные лимиты
хранилища и порог предупреждения о retention. Числа retry и начальные лимиты
батча уже определены выше; их изменение — отдельное изменение контракта.
