# Формат доставки v1

Статус: целевой контракт v1, 2026-10-27. Архитектура —
[DESIGN.md](DESIGN.md), управление подписками —
[subscriptions-api.md](subscriptions-api.md). Заголовки и подпись следуют
[Standard Webhooks](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md).

## 1. HTTP-запрос и ответ

POST на текущий URL подписки через Smokescreen. Редиректы не выполняются.
Таймаут всей попытки — 15 секунд. Тело — UTF-8 JSON без HTTP-сжатия.

| Заголовок | Значение |
|---|---|
| `Content-Type` | `application/json` |
| `User-Agent` | `ton-webhooks/<версия>` |
| `webhook-id` | случайный ID батча, сохранённый до первой отправки (§4) |
| `webhook-timestamp` | время этой попытки, unix-секунды |
| `webhook-signature` | `v1,<base64>`; при ротации две подписи через пробел |

Подпись — HMAC-SHA256 от `<webhook-id>.<webhook-timestamp>.<сырые байты тела>`.
Ключ — base64-декодированный секрет без `whsec_`. Подпись и timestamp заголовка
вычисляются заново на каждую попытку. Body и webhook-id для retry неизменны,
в том числе после перезапуска worker, смены URL и ротации секрета.

Ротация длится 24 часа: подписываем старым и новым секретом. До её завершения
вторую ротацию начать нельзя. Тело не содержит секретов и не пересобирается
для смены подписи.

| Ответ/ошибка | Действие для событийного батча |
|---|---|
| `2xx` | атомарный ACK текущего батча: сохранить cursor и удалить pending |
| `410 Gone` | сразу paused/endpoint_gone, pending сохраняется |
| `413 Payload Too Large` | сразу paused/payload_too_large, pending сохраняется |
| `429`, `502`, `503`, `504` | retry с учётом Retry-After |
| остальные не-2xx, включая `3xx` | retry без перехода по Location |
| timeout, DNS/TCP/TLS error, блокировка прокси | retry |

Расписание после последовательных отказов: 5 секунд, 30 секунд, 2 минуты,
10 минут, затем 1 час, умноженные на jitter 0.8…1.2. Для перечисленных кодов
валидный Retry-After разбирается как секунды или HTTP-date; прошедшая дата
означает ноль. Подсказка ограничивается одним часом; итог — максимум её и
расписания с jitter. Невалидный заголовок игнорируется.

После 24 часов непрерывных отказов подписка становится paused/endpoint_failing
по дедлайну, не дожидаясь следующей попытки. Успешный ACK или явный переход
paused → active начинает новый цикл. Resume сбрасывает consecutive_failures,
но сохраняет общий номер attempt батча. Повтор resume active-подписки его не
сбрасывает. Pause не отменяет уже начатую попытку; её актуальный ACK ещё может
быть принят. Ответ с устаревшим lease token или от прежнего владельца аренды
состояние не меняет.

Для ошибок сохраняются первые 512 байт ответа как безопасный текст; остальное
тело не читается. Успешное тело игнорируется. HTTP-логи — диагностика за
7 дней, а не архив payload или источник учёта оплат.

## 2. Оболочка батча

Пример сокращает только значения для документации; реальный `transaction`
всегда полный. Строки курсоров в примерах условные.

```json
{
  "type": "events.batch",
  "timestamp": "2026-10-27T10:00:04Z",
  "data": {
    "subscription_id": "0192f0c4-7d3e-7c4b-9a51-6f2d8e1b4a10",
    "network": "mainnet",
    "stream": "transactions",
    "config_version": 7,
    "from_cursor": "cursor-a",
    "cursor": "cursor-b",
    "range": {"from_mc_seqno": 51234561, "to_mc_seqno": 51234567, "partial": false},
    "head_mc_seqno": 51234570,
    "events": [
      {
        "id": "tx:mainnet:<transaction_hash>",
        "type": "transaction",
        "mc_seqno": 51234562,
        "matched_addresses": ["0:0123456789ABCDEF0123456789ABCDEF0123456789ABCDEF0123456789ABCDEF"],
        "transaction": {"...": "полный models.Transaction из ton-index-go"}
      }
    ]
  }
}
```

| Поле | Смысл |
|---|---|
| `type` | events.batch; тест — webhook.test (§6) |
| `timestamp` | время сборки этого тела, фиксируется вместе с ним; не время очередного HTTP и не время блока |
| `subscription_id` | подписка, которой принадлежит батч |
| `network` | mainnet/testnet, сеть развёртывания |
| `stream` | transactions или jetton_transfers, равен event_type подписки |
| `config_version` | конфигурация, по которой отобраны сохранённые события |
| `from_cursor`, `cursor` | точный покрытый интервал `(from_cursor, cursor]` |
| `range` | первая/последняя сканируемая mc-позиция; partial=true, если конец внутри блока |
| `head_mc_seqno` | граница готовности при исходном чтении диапазона; retry сохраняет это значение |
| `events` | непустой упорядоченный список полных событий |

В теле нет epoch, address_book, metadata и lease_token. Lease token используется
внутри сервиса для защиты состояния, не для идентификации блокчейн-события.
URL и секрет тоже не являются частью тела.

Range — диагностическое описание, курсоры определяют точные границы.
Батч может начинаться или заканчиваться внутри блока и покрывать несколько
блоков; `partial` описывает только конец. Полностью проверенные пустые блоки
тоже могут входить в интервал. Пустой батч не отправляется. Накопленный пустой
прогресс в штатном режиме сохраняется каждые 30 секунд с проверками версии,
аренды и исходного cursor либо покрывается следующим батчем.
При сбоях checkpoint может отставать больше 30 секунд. `from_cursor` берётся
из сохранённой позиции, не из позиции сканирования в памяти. Поэтому
не сохранённый отдельно пустой префикс входит в батч, а после отдельного
checkpoint `from_cursor` следующей доставки может быть позже cursor предыдущей.

## 3. События

### 3.1. Transaction

Одно событие — одна finalized-транзакция, включая неуспешную. Поля оболочки:

- `id`: `tx:<network>:<transaction_hash>`;
- `type`: `transaction`;
- `mc_seqno`: `transaction.mc_block_seqno`;
- `matched_addresses`: совпавший `transaction.account`;
- `transaction`: полный общий `models.Transaction`, как в v3.

Включаются description, block reference, входящее и все исходящие сообщения,
их `message_content` с телами и декодированным представлением по правилам
v3, `init_state`, `account_state_before` и `account_state_after`. Не вводится
облегчённая схема без тел или получение обязательных деталей по ссылке.

Состояния соответствуют хешам before/after конкретной транзакции, а не
последнему состоянию аккаунта. Текущий индексер не сохраняет все промежуточные
состояния внутри блока: тогда, как в v3, объект state содержит hash с
незаполненными прочими полями. Исторические code/data BOC для каждого такого
состояния не обещаются. Nullable/omitempty-поля остаются в семантике моделей
`ton-index-go`; это не разрешение терять ожидаемые тела сообщений при сбое
Kvrocks. Неподдерживаемый декодер может оставить decoded пустым, но raw body
должен быть загружен, если сообщение содержит ссылку на него.

### 3.2. Jetton transfer

Одно событие — подтверждённое зачисление обычного перевода между
поддерживаемыми jetton-wallets, распознанного индексером в `jetton_transfers`.
Структура:

```json
{
  "id": "jetton_transfer:mainnet:<receiver_transaction_hash>",
  "type": "jetton_transfer",
  "mc_seqno": 51234567,
  "matched_addresses": ["0:0123456789ABCDEF0123456789ABCDEF0123456789ABCDEF0123456789ABCDEF"],
  "jetton_transfer": {"...": "полный models.JettonTransfer из ton-index-go"},
  "sender_transaction": {"...": "полный models.Transaction отправляющего jetton-wallet"},
  "receiver_transaction": {"...": "полный models.Transaction принимающего jetton-wallet"},
  "receipt": {
    "internal_message_hash": "<message_hash>",
    "receiver_wallet": "0:ABCDEF0123456789ABCDEF0123456789ABCDEF0123456789ABCDEF0123456789",
    "amount": "123456789"
  }
}
```

Оба Transaction включают те же полные данные и account state, что §3.1.
JettonTransfer сохраняет исходные имена, типы и семантику полей v3: query_id,
source, destination, amount, source_wallet, jetton_master, реквизиты
отправляющей транзакции, custom/forward payload и их decoded-поля, trace_id
и остальные поля общей модели.

| Поле | Смысл |
|---|---|
| `mc_seqno` | блок принимающей транзакции, то есть момент подтверждённого зачисления |
| `jetton_transfer.transaction_hash/lt/now` | реквизиты отправляющего jetton-wallet, как в v3 |
| `jetton_transfer.amount` | запрошенная сумма из исходной таблицы |
| `receipt.amount` | полученная сумма из тела internal_transfer, строка в минимальных единицах |
| `receipt.internal_message_hash` | точная связь исходящего и входящего сообщений |
| `receipt.receiver_wallet` | проверенный jetton-wallet владельца-получателя |
| `matched_addresses` | уникальные владельцы, совпавшие с фильтром direction |

Сервис связывает сообщения по msg_hash, проверяет правильный wallet/owner/master
и успешность принимающей транзакции; алгоритм — DESIGN.md §5.2. Query_id не
используется как уникальный идентификатор. В v1 нет события неудачной попытки
jetton_transfer: её можно увидеть в потоке transactions.

Sender в блоке 100 и receiver в 103 дают одно событие с `mc_seqno=103`,
ID по receiver hash и реквизитами sender из блока 100 внутри JettonTransfer.
Событие отправляется только после появления receiver и готовности полного
payload при `head >= 103`. Если receiver появляется в следующем блоке,
правило то же; фиксированного ожидания одного блока нет. До появления receiver
события о зачислении нет, в том числе при direction=outgoing.
Worker обнаруживает receiver при обходе новых блоков, не ждёт изменения
старой строки `jetton_transfers` и не удерживает курсор на блоке sender.

После проверки готовности найденный sender без распознанной записи
`jetton_transfers` даёт внутреннее исключение `unrecognized_transfer`,
учитываемое в метриках, без webhook. Отсутствие самого sender, обязательного
тела или проверочного контекста не разрешает такой пропуск: это ожидание
источника либо явная остановка по DESIGN.md §5.2. Ещё не появившийся receiver
не считается отсутствующим обязательным контекстом уже найденного события.

Перевод внутри swap имеет ту же семантику, что самостоятельный. Классификация
actions и завершение всего trace не требуются. Уведомление подтверждает
зачисление на jetton-wallet, а не успех дальнейшего swap/вызова контракта.
Отсутствие transfer_notification не мешает зачислению. Mint, burn и
неподдерживаемые реализации не выдаются как такие события.

Source owner и destination owner сравниваются с набором подписки. При
incoming совпадает destination, при outgoing — source, при both допустимы
оба. Если адресов совпало несколько или перевод сделан себе, событие всё
равно одно. `matched_addresses` нормализуется, уникализируется и сортируется
по байтам адресов. Master фильтруется отдельно, в этот список не добавляется.

## 4. Порядок, идентификаторы и дубли

Порядок транзакций — `(mc_seqno, lt, transaction_hash)`. Порядок jetton —
`(receiver_mc_seqno, receiver_lt, receiver_transaction_hash)`. Хеши в ключе
сравниваются по байтам; в JSON используется каноническая форма HashType v3.
Одно входящее сообщение принимающей транзакции соответствует одному
подтверждённому переводу, поэтому receiver hash достаточен в ID этого типа.

ID события не зависит от подписки, набора адресов, номера попытки, границ
батча или наличия распознанного swap. Сеть входит в ID. Перечитывание другой
подпиской сохраняет эти ID; matched_addresses может различаться
между подписками. Обновление декодеров также может менять производные поля
при новом чтении. ID обозначает событие блокчейна, не ревизию его JSON.

`webhook-id` — `msg_` и криптографически случайные 128 бит в hex, с проверкой
уникальности при сохранении. Генерируется один раз вместе с body до первого
HTTP. Не вычисляется заново из тела, head или времени.

Сервис не запускает следующий батч до ACK текущего.
При смене worker, таймаутах и отзыве аренды запоздавшие HTTP-запросы
всё же возможны.
Дедупликация по webhook-id отсекает точные retry, но не заменяет дедупликацию
по ID событий: новая подписка может иначе сгруппировать их.
Порядка между подписками нет, в том числе между transactions и jetton_transfers.

После создания pending batch неизменны все байты тела, включая timestamp,
head, config_version и matched_addresses. Фильтры и адреса меняются только
на паузе; изменения применяются после всего подготовленного диапазона,
а не к сохранённому телу. Поэтому удалённый адрес ещё может присутствовать в retry.

## 5. Размер, cursor и ответ 413

По умолчанию максимум 500 событий и целевые 1 MiB (1 048 576 байт) полного
JSON с оболочкой. Лимиты подписки можно уменьшить. Большой mc-блок делится
сразу в v1, cursor сохраняет ключ последнего обработанного события.

Событие не делится. Если оно одно превышает целевой размер, отправляется
отдельный полный батч сверх max_bytes. Никаких полей события не отбрасываем,
не заменяем payload ссылкой и не обрезаем тела/state. Это требует достаточного
лимита HTTP-приёмника. Сервис не обещает, что любое событие поместится в 1 MiB.

При 413 pending сохраняется и подписка становится `paused/payload_too_large`.
Клиент увеличивает лимит endpoint либо меняет URL на паузе на подходящий
приёмник, затем вызывает resume. В обоих случаях отправляются те же байты
и webhook-id; timestamp заголовка и подпись вычисляются заново.
Смена URL атомарно отзывает аренду с увеличением lease_token и отсекает старый
ACK, как описано в subscriptions-api.md §4.2.

В v1 нет автоматического или ручного разделения уже сохранённого батча.
Уменьшение max_bytes/max_events действует только на будущие батчи и не
устраняет 413 текущего pending. До его ACK подписка не переходит к следующему
диапазону. Приёмник должен принять полный сохранённый payload; то же правило
действует для одиночного события больше целевого размера.

Pending переживает перезапуск и может доставляться после удаления исходных
блоков из hot. Его ACK покрывает весь сохранённый диапазон, включая пустой
префикс или конец. Доступность следующего незаготовленного диапазона
проверяется после ACK. Автоматического TTL нет; DELETE подписки отменяет
pending и дальнейшую доставку.

## 6. Test

Тестовая доставка имеет отдельную структуру:

```json
{
  "type": "webhook.test",
  "timestamp": "2026-10-27T10:00:00Z",
  "data": {
    "subscription_id": "0192f0c4-7d3e-7c4b-9a51-6f2d8e1b4a10",
    "network": "mainnet",
    "stream": "jetton_transfers"
  }
}
```

Подпись и HTTP-правила те же, но автоматических повторов test нет. Он
разрешён только на паузе без suspended и не изменяет cursor, pending,
цикл отказов или статус, включая ответы 410/413. Результат получает вызывающий
API клиент; подробности — subscriptions-api.md §4.5.

## 7. Как клиенту принимать доставки

1. Проверить Standard Webhooks подпись по сырым байтам тела, допустимость
   timestamp заголовка и ожидаемую подписку/сеть. JSON не пересериализуется
   до проверки. При ротации достаточно одной валидной подписи своим ключом.
2. Надёжно принять батч: обработать и сохранить результаты с дедупликацией
   по events[].id либо положить его в долговечную очередь. Только после этого
   вернуть 2xx. Простого помещения в память недостаточно.
3. При необходимости порядка обрабатывать очередь последовательно;
   запоздавший retry может прийти после более нового подтверждённого батча.
4. Хранить webhook-id для точных повторов и ID событий для пересечений.
   Разрыв курсоров из-за сохранённого пустого диапазона не доказывает
   потерю событий.
5. Сохранять cursor/позицию для диагностики и выбора `start_mc_seqno` новой
   подписки при восстановлении. В v1 нет seek/after_cursor, поэтому повтор
   можно начать с известного блока включительно и убрать дубли по ID.
6. Отслеживать статус подписки через API и уведомления приватной стороны.
   Resume не перескакивает на голову; expired требует явного восстановления.
7. Игнорировать неизвестные добавочные поля совместимой версии. Test
   обрабатывать отдельно от событийных батчей.

## 8. Совместимость

Объекты Transaction и JettonTransfer используют общие модели `ton-index-go`.
Совместимые новые поля могут добавляться, но смысл существующих полей не
меняется. Переключателей include_address_book/include_metadata в v1 нет.

Новый тип событий требует новой подписки: event_type существующей неизменяем.
Несовместимое изменение внешнего формата вводится отдельной версией
контракта и включается явно. Релиз сервиса не изменяет байты уже сохранённых
батчей. Клиент не должен ожидать, что новая историческая подписка побайтно
воспроизведёт ранее доставленный JSON:
источник и декодеры могут быть обновлены, а архив успешных тел не хранится.
