# Формат доставки

Статус: черновик для ревью, 2026-10-19. Основа — [DESIGN.md](DESIGN.md) и
[subscriptions-api.md](subscriptions-api.md). Заголовки и подпись следуют
[Standard Webhooks](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md).

## 1. Запрос

`POST` на URL подписки.

| Заголовок | Значение |
|---|---|
| `Content-Type` | `application/json` |
| `User-Agent` | `ton-webhooks/<версия>` |
| `webhook-id` | идентификатор доставки (§4) |
| `webhook-timestamp` | время попытки, unix-секунды |
| `webhook-signature` | `v1,<base64>`; во время ротации секрета — две подписи через пробел |

Подпись — HMAC-SHA256 от строки `<webhook-id>.<webhook-timestamp>.<тело>`.
Ключ — секрет подписки без префикса `whsec_`, декодированный из base64.
`webhook-timestamp` и подпись вычисляются заново на каждую попытку, тело и
`webhook-id` при повторе не меняются.

### Ответ

| Ответ | Что делаем |
|---|---|
| `2xx` | батч принят, курсор сдвигается |
| `410 Gone` | подписка встаёт на паузу с причиной `endpoint_gone`, как требует Standard Webhooks |
| `429`, `502`, `503`, `504` | повтор с увеличенной задержкой; заголовок `Retry-After` учитывается |
| другие коды, `3xx`, таймаут, ошибка соединения | повтор того же батча по расписанию |

- Редиректы не выполняются, `3xx` — ошибка: клиент должен поменять URL
  подписки, а не перенаправлять на другой хост.
- Тело ответа не читается. Для неуспешных попыток первые 512 байт попадают в
  журнал доставок.
- Таймаут — 15 секунд, нижняя граница рекомендации Standard Webhooks.
  **Открыто:** окончательное значение.
- Сжатия тела нет: многие serverless-приёмники не распаковывают тело запроса.

## 2. Тело

```json
{
  "type": "events.batch",
  "timestamp": "2026-10-19T10:00:04Z",
  "data": {
    "subscription_id": "0192f0c4-7d3e-7c4b-9a51-6f2d8e1b4a10",
    "stream": "transactions",
    "epoch": 1,
    "range": {"from_mc_seqno": 51234561, "to_mc_seqno": 51234567, "partial": false},
    "cursor": "AQEDDccH",
    "head_mc_seqno": 51234570,
    "events": [
      {
        "id": "tx:mO2Xv…=",
        "type": "transaction",
        "mc_seqno": 51234562,
        "matched_addresses": ["0:5B3A…"],
        "transaction": {"…": "объект Transaction, как в /api/v3/transactions"}
      }
    ],
    "address_book": {"…": "только при options.include_address_book"},
    "metadata": {"…": "только при options.include_metadata"}
  }
}
```

| Поле | Смысл |
|---|---|
| `type` | `events.batch`; тестовая доставка — `webhook.test` (§6) |
| `timestamp` | время последнего блока диапазона (`gen_utime` блока `to_mc_seqno`), а не время отправки: так тело одинаково на всех повторах |
| `subscription_id` | подписка, которой принадлежит батч |
| `stream` | поток: `transactions` или `actions`. Батч содержит события одного потока (DESIGN.md §4) |
| `epoch` | эпоха хранилища; при смене клиент пересинхронизируется (subscriptions-api.md §4.3) |
| `range` | mc-блоки, которые покрывает батч, включительно; `partial` — см. §5 |
| `cursor` | позиция потока после батча; нужна для `seek` |
| `head_mc_seqno` | граница готовности потока на момент сборки батча; разница с `to_mc_seqno` — отставание потока |
| `events` | события в порядке из §3 |
| `address_book`, `metadata` | обогащение как в v3 для всех адресов батча; на фильтрацию не влияет |

Батч покрывает и блоки без событий: диапазон доходит до последнего
обработанного блока. Батч без событий не отправляется.

## 3. События

Одно событие — одна транзакция или один action. Группировки по трейсу нет:
`trace_id` есть внутри объектов транзакции и action, по нему клиент связывает
события сам. Батч потока `actions` устроен так же, только события в нём —
actions.

| Поле | Транзакция | Action |
|---|---|---|
| `id` | `tx:<hash>` | `action:<action_id>` |
| `type` | `transaction` | `action` |
| `mc_seqno` | `mc_block_seqno` транзакции | `trace_mc_seqno_end`: блок, в котором завершился трейс |
| `matched_addresses` | `account` транзакции | адреса подписки среди `accounts` action |
| объект | `transaction`: как в v3, с входящим и исходящими сообщениями и их телами | `action`: как в v3, в рендеринге под `supported_action_types` подписки |

`matched_addresses` избавляет клиента от поиска, какой из его адресов
совпал: для action с миллионом адресов в подписке это не очевидно.

### Порядок

1. По `mc_seqno` по возрастанию.
2. Внутри блока транзакции — по `lt`, затем по хэшу; actions — по `end_lt`,
   затем по `action_id`.

Порядок детерминирован: одинаковые блоки с одинаковым фильтром всегда дают
одинаковую последовательность. Порядка между потоками нет: action приходит по
блоку завершения трейса и может прийти позже транзакций следующих блоков.

### Что не приходит

- Actions незавершённых трейсов. Action приходит один раз, в блоке завершения
  трейса.
- Actions трейсов больше 4 000 узлов и трейсов, на которых классификатор упал.
  Транзакции этих трейсов приходят как обычно — они остаются источником
  истины.
- Повторно — actions, которые классификатор пересчитал задним числом.

## 4. Идентификаторы и дубли

- **`id` события** стабилен навсегда. Хэш транзакции уникален. `action_id` —
  SHA-256 от хэша корневого сообщения и типа action, поэтому тоже уникален.
- **`webhook-id`** — `msg_` и первые 128 бит SHA-256 от `subscription_id` и
  тела запроса, в hex. Повтор того же батча даёт тот же `webhook-id`, как
  требует Standard Webhooks. Если содержимое изменилось — например, после
  перемотки с дополненным набором адресов или с обновлённым обогащением, —
  `webhook-id` другой, и клиент не отбросит новые события как дубль.

Дубли событий возникают при повторах, при смене worker, ведущего подписку,
при перемотке назад и при пересинхронизации после смены эпохи. Батчи могут
перекрываться, поэтому надёжная дедупликация — только по `id` события.
Дедупликация по `webhook-id` — оптимизация, которая отсекает точные повторы.

Гарантия порядка — внутри потока: новое событие никогда не приходит раньше
более старого, кроме повторов уже доставленного.

## 5. Размер батча

- Не больше 1 МБ тела и 1 000 событий. **Открыто:** значения.
- В батч целиком входят mc-блоки, пока лимит не превышен, но хотя бы один блок.
- Если события одного блока не помещаются в лимит, блок делится на несколько
  батчей. У такого батча `from_mc_seqno = to_mc_seqno` и `partial: true`, если
  блок продолжится в следующем. Курсор хранит ключ сортировки последнего
  доставленного события блока (§3), а не его номер: если между попытками
  изменится фильтр, продолжение не пропустит и не повторит события.
- Событие, которое одно больше лимита, отправляется отдельным батчем без учёта
  лимита: делить событие нельзя.

Standard Webhooks советует держать тело в пределах примерно 20 КБ и для
больших данных отдавать ссылку. Мы отступаем от этого сознательно:
доставка строго по порядку, по одному запросу в полёте, и публичной ручки, по
которой клиент мог бы забрать данные по ссылке, нет. Без батчей подписка с
потоком событий не успевала бы за сетью.

## 6. Тестовая доставка

```json
{
  "type": "webhook.test",
  "timestamp": "2026-10-19T10:00:00Z",
  "data": {"subscription_id": "0192f0c4-7d3e-7c4b-9a51-6f2d8e1b4a10"}
}
```

Те же заголовки и подпись, что у обычной доставки. Курсор не трогается.

## 7. Как клиенту принимать доставки

1. Проверить подпись библиотекой Standard Webhooks: они есть для Go, Python,
   JavaScript/TypeScript, Java, Rust, PHP, Ruby, C# и проверяют допуск по
   времени. Подпись проверяется по сырому телу запроса: разобрать JSON и
   сериализовать заново нельзя, байты разойдутся.
2. В одной транзакции своей базы пропустить события с уже виденным `id`,
   обработать остальные и записать их `id`.
3. Ответить `2xx` только после коммита. Если обработка дольше таймаута,
   положить батч в свою очередь и ответить сразу.
4. Сохранить `cursor` каждого потока и `epoch`. Курсор понадобится для `seek`
   после своей аварии: `after_cursor` перематывает поток, которому
   принадлежит курсор. Если `epoch` изменился, заново добавить весь набор адресов и
   перемотать подписку (subscriptions-api.md §4.3).
5. Игнорировать неизвестные поля: новые поля добавляются без предупреждения.

## 8. Совместимость

- Новые поля в теле и в объектах событий добавляются без смены версии.
- Новые типы событий приходят, только если клиент добавил их в `event_types`
  подписки.
- Рендеринг actions зафиксирован `supported_action_types` подписки и с
  релизами не меняется.
- Несовместимое изменение тела выйдет под новым `type` батча, например
  `events.batch.v2`, и включается на подписке явно.
