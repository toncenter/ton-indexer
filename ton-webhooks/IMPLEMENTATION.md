# План реализации ton-webhooks

Статус: план работ по согласованному дизайну v1, 2026-10-27. Сервис ещё не
реализован. Продуктовый контракт задают [DESIGN.md](DESIGN.md),
[subscriptions-api.md](subscriptions-api.md) и
[delivery-format.md](delivery-format.md); этот документ определяет порядок
работ, границы компонентов и критерии готовности.

Первый сквозной результат — подписка на `transactions`, которая сохраняет
полный payload, доставляет его и переживает перезапуск. Это внутренний этап,
не сокращённый публичный релиз. В v1 также обязательны подтверждённые
`jetton_transfers`, test, ротация и общий outbox для управления и учёта ACK.
При 413 v1 сохраняет pending и ставит подписку на паузу; разделения уже
сохранённого батча нет.

## 1. Разделение реализации

Добавляем отдельный Go-модуль `github.com/toncenter/ton-indexer/ton-webhooks`
с локальной зависимостью на `../ton-index-go`, как у других Go-сервисов
репозитория. Версию Go выравниваем с `ton-index-go/go.mod`.
Один бинарник запускается с ролью `api` или `worker`; миграции выполняются
отдельной командой `migrate`, а не каждым процессом при старте.

Предлагаемое размещение нового кода:

```text
ton-webhooks/
  main.go, go.mod, go.sum, CMakeLists.txt
  migrations/              SQL-миграции отдельной БД сервиса
  internal/domain/         cursor, события, фильтры, ошибки и состояния
  internal/source/         finalized reader, распознавание jetton, сборка событий
  internal/store/          транзакционные команды, leases, pending, outbox
  internal/api/            клиентские и административные методы
  internal/routing/        индекс адресов, live-сканирование и догон
  internal/delivery/       точные байты JSON, подпись и HTTP через proxy
  internal/worker/         планирование, retry и переходы состояния
  internal/config/         конфигурация ролей, DSN, ключей и proxy
  internal/observability/  метрики, health и диагностические логи
  integration/             сценарии с реальными Postgres/Kvrocks и HTTP endpoint
  testdata/                обезличенные блоки, сообщения и эталонные payload
```

В `ton-index-go/index/crud` добавляем узкий общий механизм строгого чтения
и загрузки полных моделей. Правила подписок, cursor, подтверждение jetton
и HTTP-оболочка остаются в `ton-webhooks`. Не создаём вторую копию
`models.Transaction`, `models.JettonTransfer` и их сериализации.

Соединения разделены: read-only DSN hot-индексера, выбранный узел Kvrocks
и собственный read-write DSN БД сервиса. Для последней нужен отдельный pool:
текущий `crud.makePool` регистрирует типы `pgton` и другие типы индексера,
которых в БД подписок нет. Между двумя БД нет join и общей транзакции.

## 2. Этапы и зависимости

Независимые ветки можно разрабатывать одновременно. Номера обозначают
результаты, а не обязательную последовательность всех работ.

| Этап | Зависимости | Проверяемый результат |
|---|---|---|
| E0. Проверка источников | Согласованный дизайн | Поддерживаемые jetton-wallets, доказательство зачисления на реальных данных, SQL-планы и список необходимых доработок индексера |
| E1. Каркас и внутренние контракты | Согласованный дизайн | Собираемый бинарник, изолированная конфигурация, формат cursor и интеграционный стенд |
| E2. Строгий reader и transactions | E1; проверки границ/payload/SQL из E0 | Полные события из согласованного finalized-диапазона без скрытого cold fallback |
| E3. Подтверждённые jetton transfers | E2, результаты E0 | Переводы по позиции получателя, включая переводы внутри swap |
| E4. Долговечное состояние | E1 | Миграции и атомарные команды, защищённые версиями и арендой |
| E5. Первый сквозной поток | E2, E4 | API настройки подписки и worker для transactions с подписью, ACK и retry |
| E6. Полный контракт v1 | E3, E5 | Оба потока, все методы API и точные переходы состояния |
| E7. Совместное чтение и нагрузка | E3, E5 | Индекс адресов, разделение live/догон и измеренные ресурсные бюджеты |
| E8. Инфраструктура и приватная часть | Начинается с E1/E4; завершается после E6/E7 | Gateway, proxy, экспорт общего outbox, мониторинг, HA и восстановление |
| E9. Проверки отказов и запуск | E6, E7, E8 | Пройденные сценарии отказов, canary и проверенная процедура отката |

Критический путь по данным: E0 → E2 → E3 → E6 → E9.
По доставке: E1 → E4 → E5 → E6 → E9. E7 и E8 также блокируют публичный
запуск; их нельзя оставлять на период после релиза.

## 3. E0 — проверить источники до основной разработки

Цель — закрыть неопределённости конкретными примерами и запросами. Результат
этапа: воспроизводимые SQL-пробы, набор fixtures и короткая запись решений
о поддерживаемых кошельках и необходимых изменениях схемы индексера.
Проверки общих источников и jetton выполняются независимо: незакрытый вопрос
исторической идентификации кошелька не мешает реализации transactions.

1. Проверить на используемой версии индексера непрерывную границу
   `_ton_indexer_progress.finalized_mc_seqno`, границу hot и наличие watermark
   `ton-index:v1:progress:finalized_mc_seqno` на каждом выбранном узле Kvrocks.
   Механизмы уже есть в коде; новая граница классификатора для webhook не нужна.
2. Собрать примеры обычного перевода, перевода внутри swap, получения без
   notification, отправки и получения в следующем и более позднем mc-блоке,
   bounce, ошибки получателя, mint и неподдерживаемого кошелька. Добавить
   sender без распознанной записи `jetton_transfers` при готовом источнике.
   Для каждого зафиксировать строки таблиц, тела сообщений и ожидаемый результат.
3. Выполнить связь receiver → incoming `msg_hash` → outgoing message → sender
   transaction → `jetton_transfers`. Проверить случай, когда принимающий блок
   ещё в hot, а контекст отправителя уже недоступен. Не использовать
   `query_id` или наличие action как доказательство получения.
4. Зафиксировать, откуда для каждой поддерживаемой реализации берётся
   достоверная связь wallet/master/owner на момент события. Текущий detector
   проверяет `get_wallet_address(owner)`, но актуальная запись `jetton_wallets`
   сама по себе не является историческим доказательством. Если существующих
   данных недостаточно, до E3 добавить минимальное сохранение проверочного
   контекста в индексер и описать его срок доступности. Указание точной версии
   кода кошелька и доказательство неизменности owner/master допустимы только
   для реализаций, для которых это действительно установлено.
5. Разделить обязательные объекты payload и допустимое отсутствие данных:
   известный hash тела сообщения требует тело; промежуточный account state
   может остаться объектом с hash, как в текущем v3. Зафиксировать это в
   fixtures для Postgres-only и Postgres + Kvrocks.
6. Снять `EXPLAIN (ANALYZE, BUFFERS)` на репрезентативном стенде для обхода
   блока, keyset pagination и jetton join. Проверить partition pruning,
   tie-break по hash и поиск отправителя в более ранних разделах таблиц.

Индексы добавляем по результатам измерений. Кандидаты: полный ключ
`transactions(mc_block_seqno, lt, hash)`, частичный индекс входящих
`internal_transfer` для обхода по принимающей транзакции и индекс поиска
исходящего сообщения по hash/direction. Уже есть индексы по `msg_hash`,
opcode, account и `(mc_block_seqno, lt)`; дублировать их без измерений не надо.
Порядок `tonhash` в `pgton` уже основан на `memcmp`; Go-cursor должен совпадать
с ним, а не сортировать base64-представление.

Блокирующее условие для E3: нельзя выпускать распознавание, которое
подтверждает произвольный контракт по opcode и текущему owner/master.
Список поддерживаемых реализаций — часть результата E0, не обещание
поддержать все jetton-контракты.

## 4. E1 — каркас, контракты и сборка

Добавить роли бинарника, раздельные pools, конфигурацию сети, ключа шифрования,
proxy и внешнего запрета доставки. В тестовом окружении поднять отдельную
PostgreSQL 18 для сервиса, индексерную схему с fixtures, Kvrocks и управляемый
HTTP endpoint. Для HA-сценариев E9 потребуется отдельный стенд с репликами.

Зафиксировать небольшие внутренние интерфейсы:

- Reader открывает ограниченную сессию чтения и возвращает границы источника,
  упорядоченные кандидаты, полные модели и последнюю действительно проверенную
  позицию. Результат различает готовность, известное исключение из потока и
  потерю необходимых данных; пустая страница не означает автоматически конец блока.
- Store предоставляет команды `claim`, `save pending`, `advance empty`,
  `reserve attempt`, `apply result` и команды API. Их аргументы содержат
  необходимые cursor/config_version/lease, а не позволяют вызывающему
  коду независимо обновлять связанные таблицы.
- Sender получает уже сохранённые байты, ID и параметры текущей попытки.
  Он возвращает результат HTTP и не пересобирает события.

Реализовать внутренний cursor с partial/full-block позициями, его сравнение
и внешний versioned base64url codec. Проверять network/event_type и границы
полей. Не добавлять возможность установки cursor через API.

Подключить модуль к CMake, Docker и CI сразу. Импорт CRUD тянет декодер
`ton-index-go/index/detect/marker.go` с CGO и `ton-marker`: новый образ должен
содержать нужные библиотеки, а сборка — зависеть от их сборки. Проверка запуска
готового образа обязательна; одного `go build` в окружении разработчика мало.

Готовность: обе роли стартуют с валидной конфигурацией, миграционная команда
работает на пустой БД, интеграционный стенд воспроизводим, cursor одинаково
сортируется в Go и SQL. Начальные миграции состояния завершаются в E4.

## 5. E2 — строгий reader и полные transactions

В `ton-index-go/index/crud` выделить opt-in путь строгого чтения без изменения
поведения существующего REST API. Высокоуровневый `QueryTransactions` сейчас
включает API-пагинацию, enrichment и маршрутизацию hot/cold; напрямую вызывать
его из worker недостаточно.

Необходимые изменения общей библиотеки:

- Передавать `context.Context` и узкий SQL-интерфейс, реализуемый `pgx.Tx`,
  в используемые низкоуровневые scan/enrich helpers. Сейчас часть helpers
  привязана к `*pgxpool.Conn` и внутреннему `context.Background()`.
  Рефакторить только цепочку, нужную reader, без переписывания всего CRUD.
- Читать progress, наличие mc-блоков и строки событий в одной read-only
  `REPEATABLE READ` транзакции с одного hot-узла. Обходить диапазон небольшими
  страницами и не удерживать snapshot во время HTTP-доставки.
- Для Kvrocks выбрать узел, проверить его собственный watermark и закрепить
  чтение за ним. Текущий механизм допускает fallback/refill; в строгом режиме
  смена узла требует повторной проверки и пересборки незаписанного результата.
  Отсутствующий watermark или обязательный объект — ошибка готовности.
- Переиспользовать загрузку message content, init state и исторических account
  states, декодеры и общие модели. Не подставлять последнее состояние аккаунта.
  Допустимый hash-only state не блокирует поток; потерянное ожидаемое тело
  сообщения блокирует. Не обращаться к address book и metadata.

В `internal/source` реализовать обход transactions по составному ключу,
фильтрацию account/opcode, `matched_addresses`, устойчивый ID события и
сборку полного объекта. Разделить выбор кандидатов и загрузку тяжёлого payload,
чтобы не декодировать все тела сети для каждой подписки. Неподдерживаемое
декодером тело сохраняется в исходном виде согласно семантике v3; отсутствие
декодирования не разрешает удалить исходный BOC.

Проверки этапа: несколько страниц одного блока без пропусков/дублей, одинаковый
lt у разных транзакций, пустые блоки, rollback head, отсутствие одного
обязательного объекта, смена Kvrocks-узла, допустимый hash-only state.
Полный JSON моделей сравнивается с сериализацией `ton-index-go` на тех же
fixtures; существующие тесты затронутых CRUD/декодеров остаются зелёными.

## 6. E3 — подтверждённые jetton transfers

Добавить Go-разбор `internal_transfer` (`0x178d4519`) через существующие
TON cell primitives. Если parser полезен другим потребителям, разместить
его в `ton-index-go/index/parse`; Python-классификатор в runtime не включать.

Reader начинает с входящих сообщений принимающих транзакций и выполняет
связь, проверенную в E0. Sender в блоке 100 без receiver не запускает доставку
и не удерживает cursor на блоке 100. Reader продолжает читать новые блоки;
когда receiver появился в 101 или 103 и его блок доступен по head, связывает
его с sender из 100 и только после проверки зачисления создаёт событие.
Поиск sender не ограничивается текущим диапазоном receiver. Для outgoing
тот же результат маршрутизируется по owner отправителя. Очередь ожидания
sender, таймер «через один блок» и ожидание обновления старой строки
`jetton_transfers` не нужны.

Этапы разрешения связи должны сохранять причину отсутствия строки; inner
join не должен незаметно терять кандидатов. После проверки готовности
источника найденный sender без записи `jetton_transfers` означает явное
исключение `unrecognized_transfer` с метрикой. Поток покрывает распознанные
индексером переводы с подтверждённым получением. Отсутствие самого sender,
обязательного тела или проверочного контекста не относится к этому исключению:
временно недоступные данные дают source_not_ready, установленная потеря —
source_data_unavailable. За такого неразрешённого кандидата cursor не движется.
Пока receiver вообще не появился, кандидата ещё нет и блокировка источника
по этому переводу не выставляется.

Реализовать все проверки DESIGN.md §5.2: sender, принадлежность сообщения,
не-bounced input, поддерживаемый wallet/master/owner, compute/action success
получателя и finalized-граница. Не ждать actions, полного trace, notification
или excesses. По получателю определяются cursor и ID; из `internal_transfer`
берётся `receipt.amount`, исходный `JettonTransfer.amount` не изменяется.

Применять owner addresses, direction и master-фильтр до загрузки тяжёлых
моделей, где это возможно без ослабления проверки. Для совпадения обоих
владельцев и перевода себе выдавать одно событие. Использовать общий loader
E2 для полных sender/receiver transactions и общий loader JettonTransfer,
включая custom/forward payload. Ошибка полноты любой части не превращается
в частичное успешное событие.

Готовность: все fixtures E0 дают ожидаемые результаты, включая swap с
недоступным классификатором и нулевым forward amount. Поэтапная публикация
sender в N и receiver в N+1/N+3 подтверждает отсутствие ранней доставки,
продвижение по промежуточным блокам и выдачу события по receiver даже после
перезапуска worker. Потеря sender старше hot останавливает подписку, а найденный
sender без распознанной записи при готовом источнике учитывается как исключение.
Mint/burn и доказанные неуспехи не становятся успешным transfer.

## 7. E4 — БД сервиса и атомарные команды

Превратить целевую схему subscriptions-api.md §6 в версионированные миграции.
Миграциями владеет `ton-webhooks`, а не `ton-index-postgres-migrate`.
Добавить необходимые ограничения и индексы для реальных запросов, проверить
повторный запуск мигратора и обновление с предыдущей версии.

Реализовать транзакции состояния до HTTP-worker:

1. Создание owner/подписки/delivery_state/постоянной строки leases; owner lock
   для квот и suspend/create. Общий порядок блокировок: owner → subscription → lease.
   Внутри каждого уровня пачки сортируются по ID.
2. Claim/renew/release с монотонным `lease_token`; новый claim и отзыв аренды
   при смене URL увеличивают token, освобождение не сбрасывает его.
   Claim, отзыв, фиксация сканирования, PATCH и ACK сериализуются строкой
   подписки. Сроки проверяются по времени БД. Renew меняет только срок аренды.
   Renew идёт ограниченными пачками с ограниченным ожиданием блокировок,
   проверяет worker_id/token/неистёкший срок и возвращает продлённые строки
   через RETURNING. Неудача пачки не задерживает все остальные; истёкшая
   аренда требует нового claim, не оживляется renew.
3. Сохранение pending и продвижение пустого диапазона с одинаковыми проверками
   active/suspend/cursor/config_version/действующей аренды.
   В штатном режиме накопленный пустой прогресс сохраняется каждые 30 секунд
   ограниченными пачками либо покрывается следующим pending. Ввести отдельный
   scan_cursor в памяти; CAS и from_cursor используют сохранённый cursor.
   При смене cursor/config_version/lease_token прогресс в памяти
   отбрасывается. Проверить повторный scan после падения и отсутствие записи
   по каждой подписке на каждый пустой блок; при сбоях checkpoint может отставать
   больше 30 секунд.
4. Резервирование попытки до HTTP с чтением текущих URL и секретов из БД;
   применение ответа только при совпадении worker_id, lease_token, webhook-id
   и действующей аренде. ACK атомарно меняет cursor, pending, ошибки и создаёт
   batch_acked в outbox, при необходимости — статус и управляющее событие.
   Изменение config_version не отменяет ACK уже сохранённого pending.
5. Идемпотентные команды с сериализацией одинакового ключа и сравнением
   канонического request hash. Секреты и сохранённые ответы шифруются внешним
   ключом; точное тело pending хранится как bytes, не jsonb.
6. Общий транзакционный outbox и одна пара claim/ACK с арендой. Экспортёр
   выбирает неподтверждённые свободные строки или строки с истёкшей арендой,
   а не всё после максимального ранее увиденного ID. Для batch_acked
   webhook_id уникален; остальные виды событий не имеют webhook_id.
   Удаление подписки не удаляет её управляющие события и учёт принятых батчей.
7. Изменение адресов только на паузе, без журнала дельт. Перед новой выборкой,
   включая первую после resume, worker сверяет config_version с БД. После
   нового claim, при отсутствии снимка или несовпадении версии загружает полный
   согласованный снимок адресов, фильтров и config_version. Resume без изменений
   не требует повторной загрузки того же набора. Доставка уже сохранённого
   pending не требует такого снимка.

Все эти записи используют `synchronous_commit=on`. Тесты должны реально
конкурировать через несколько соединений: старый worker не применяет ACK,
pause/PATCH/resume не позволяет сохранить даже пустой диапазон по старому
фильтру или адресам, параллельные create не обходят квоту. Базовые HA-условия
проверяются совместно с E8/E9.

## 8. E5 — первый сквозной поток

Сначала реализовать минимальный законченный путь настройки: create/list/get,
PATCH адресов только на паузе, pause/resume и delete. Подписка создаётся paused.
Обязательный `start_mc_seqno` принимает целое число или строку `"latest"`;
последняя однократно разрешается через reader в head + 1. В подписке хранится
и во всех ответах возвращается конкретный номер. Числовой N включает блок N;
начальный cursor — конец N−1. Идемпотентность сравнивает запрос до разрешения
`"latest"` и возвращает прежний результат и секрет, не перечитывая head.
Resume не меняет начальную позицию. Набор адресов и filters читаются
согласованно, изменения возвращают точный `effective_after_cursor`.

Затем подключить worker для transactions:

- Приоритет сохранённому pending, затем новому чтению.
  Pending доставляется даже при недоступном индексере. Сначала commit полного
  JSON и webhook-id, только затем HTTP.
- Подсчёт фактических UTF-8 байтов вместе с оболочкой; разделение блока и
  одиночное большое событие целиком. Не вводить скрытый жёсткий лимит в 1 MiB.
  Внутренние ограничения декодера учитывать разбиением его запросов, без
  усечения исходных message bodies или account state.
- Standard Webhooks HMAC по сохранённым байтам. На retry меняются timestamp
  заголовка и подпись; body и webhook-id остаются прежними.
- HTTP через Smokescreen, запрет redirects, timeout 15 секунд. Точное retry
  расписание, Retry-After, немедленные паузы 410/413 и отдельный таймер дедлайна
  24 часов реализуются по delivery-format.md, без ожидания следующего ответа.
- Перед отправкой проверяется действующая аренда и разрешение доставки.
  Ответ применяется через Store; транзакций БД на время HTTP нет.
  Журнал отражает и поздний ответ с `applied_to_state=false`.

На этом этапе достаточно одного worker и небольшого набора подписок.
Интеграционный результат: реальный endpoint получает полную transaction,
после сбоя между HTTP и ACK видит те же ID/байты, после сохранённого ACK
worker продолжает с правильной позиции. Сервис пока не готов к публичному
использованию: оставшийся контракт закрывается в E6–E9.

## 9. E6 — полный API и восстановление доставки

Подключить jetton reader к тому же worker. Отдельной очереди ожидания
получателя или отдельного протокола ACK для jetton не добавлять.
Завершить остальные методы и переходы состояния:

- Пагинация адресов, проверка наличия адреса и редактирование описания;
  единая проверка принадлежности owner для всех операций с ресурсом.
- PATCH фильтров, URL и лимитов на паузе; смена URL атомарно увеличивает
  lease_token и очищает worker_id/lease_until, отсекая прежний ACK без изменения
  байтов/ID pending. После resume нужен новый claim и чтение текущего URL
  при резервировании попытки. Реальное изменение конфигурации увеличивает её версию.
- После 413 pending остаётся неизменным на паузе. Продолжение — увеличение
  лимита приёмника либо смена URL, затем resume с прежними байтами/ID.
  Уменьшение лимитов через PATCH меняет только будущие батчи; текущий pending
  не разделяется, не перечитывается и не пропускается.
- Ротация секретов с двойной подписью на 24 часа и запретом повторной ротации
  до завершения overlap. Не менять тело и lease_token при ротации.
- Test на паузе без suspended через тот же signer/proxy, с лимитом частоты,
  сериализацией с известной текущей попыткой и без изменения cursor, учёта
  или журнала доставки.
- Истечение следующей незаготовленной позиции, ожидание source_not_ready,
  остановка source_data_unavailable и предупреждения retention. Сохранённый
  pending доставляется за границей hot; после его ACK проверяется
  следующий диапазон. Paused и suspended тоже участвуют в оценке retention.
- Административные suspend/unsuspend, список, удаление и экспорт; просмотр
  журнала попыток. Pause/suspend допускают ACK уже начатой актуальной попытки.
  Resume из paused сбрасывает цикл ошибок, resume уже active — нет.

Готовность: каждый метод из таблицы API имеет реализацию и проверку своего
существенного инварианта. Для live и догона совпадают правила
распознавания и фильтрации. Новый фильтр никогда не переписывает сохранённые
события, включая `matched_addresses`.

## 10. E7 — совместное чтение и ресурсные бюджеты

После проверки одного полного потока добавить несколько workers и общий
для подписок одного worker обход новых блоков. Читаем кандидатов один раз
на диапазон, маршрутизируем через «адрес → подписки», тяжёлые immutable
объекты переиспользуем в ограниченном кэше. Это не новый долговечный журнал.
Размер диапазона, память, число SQL/Kvrocks-запросов и concurrency ограничены.

Из streaming v2 переносим подход к индексу адресов; его `ClientManager` и
Redis replay reader не подключаем. Streaming replay использует другое
хранилище и семантику снимков и не заменяет finalized-reader E2/E3.

Для каждой обслуживаемой подписки индекс адресов имеет подтверждённую
config_version. Версия сверяется перед новой выборкой, включая первую после
resume. После нового claim, при отсутствии снимка или несовпадении версии
загружается полный согласованный снимок. Нельзя отметить
пустой диапазон обработанным, если маршрутизация была сделана по устаревшему
набору. Финальная проверка версии в Store сохраняется и после оптимизации.

Число workers задаётся конфигурацией развёртывания. Каждый ограниченными
пачками забирает свободные подписки или подписки с истёкшей арендой, соблюдая
лимит числа своих подписок и параллельных операций. Здоровый worker сохраняет
аренды; автоматического перераспределения по адресам или объёму payload нет.
Другой worker получает подписку после освобождения или истечения lease,
перечитывая долговечное состояние из БД.

Догон получает отдельные очереди и бюджеты SQL, декодирования и HTTP;
ограничения параллелизма не дают одной подписке или недоступному endpoint
занять все ресурсы. Число workers и лимиты меняет оператор по измерениям.

Измерить на согласованном профиле: миллион адресов, редкие совпадения,
множество подписок на один адрес, тяжёлые события, длительные отказы endpoints,
массовый догон и общий WAL с индексером. Отчёт фиксирует p50/p95/p99 задержки
после finalized, CPU/RAM, QPS/IO, объём pending и задержку sync commit.
По измерениям выбрать число workers, pool sizes и бюджеты live/догона.
Численный SLA до этих измерений не обещать.

Давление на хранилище снимается ограничением новых сканирований и приёма
нагрузки, а не удалением pending или обрезкой payload. До запуска
зафиксировать запас диска, пороги уведомлений и действия оператора.

## 11. E8 — развёртывание и приватные интеграции

Эту ветку начинаем до завершения worker: ей нужны отдельные договорённости
с владельцами приватного backend и инфраструктуры.

| Работа | Результат до запуска |
|---|---|
| БД сервиса в hot Patroni | Отдельная PostgreSQL 18 БД/роль/DSN, синхронная реплика, проверенные `synchronous_mode` и `synchronous_mode_strict`; влияние общего WAL измерено. Сначала `synchronous_commit=local` по умолчанию для кластера и `on` только роли сервиса, затем включение режима; проверено, что индексер не ждёт реплику и не встаёт при её падении |
| Gateway/HAProxy | Клиентские служебные заголовки удаляются; owner, квоты и доступ к admin API выставляются доверенной стороной; межвладельческий доступ проверен |
| Smokescreen и сеть | Все delivery/test проходят proxy; API/worker не могут выйти напрямую; proxy не достигает внутренней сети; DNS rebinding и redirects проверены |
| Приватный backend | Общий потребитель outbox через claim/ACK: сначала надёжно сохраняет события с дедупликацией по outbox ID, затем подтверждает экспорт. Учёт и уведомления читают принятый приватный журнал; учёт batch_acked дополнительно дедуплицируется по webhook_id |
| Конфигурация и ключи | Раздельные credentials источника/сервиса, внешний ключ шифрования с процедурой восстановления, внешнее разрешение доставки |
| Мониторинг | Метрики приложения, scrape/alerts, диагностика недоступного источника, endpoint и экспорта; понятное состояние во время запрета доставки |
| Обслуживание БД | Очистка логов через 7 дней, идемпотентных ответов после 24 часов, подтверждённых outbox через 7 дней; pending и неэкспортированные записи без TTL |
| Backup/restore | Бэкап всей БД, восстановление с запретом исходящих попыток вне восстановленной БД, сверка с приватной стороной перед разрешением доставки |

До приёма трафика проверить `SHOW synchronous_commit` из реальных pools
индексера и сервиса, включая переопределения роли/БД/сессии. Пересоздать
соединения при необходимости применения настроек роли и повторить проверку
после failover. При потере sync replica новые попытки сервиса ждут необходимого
коммита; уже начатые HTTP-запросы могут завершиться.

Минимальные метрики: source head/lag и watermark выбранного Kvrocks,
возраст/байты pending, очередь и задержка доставки, ошибки HTTP,
состояния/blocked reasons, stale ACK, lease contention, время SQL и sync
commit, исключения распознавания jetton по причине, отставание общего outbox
отдельно для управляющих событий и batch_acked, ближайшая граница retention.
Под нагрузкой проверить, что потребитель успевает принимать batch_acked
и не задерживает управляющие события сверх согласованного бюджета. Идентификаторы
подписок и адреса не использовать как неограниченные labels метрик; для
точечной диагностики есть API/логи с сокрытием секретов.

До restore необходимо остановить workers и test-доставки внешним gate.
Старый backup может вернуть устаревшие URL, секреты и удалённые подписки;
сам восстановленный outbox не достаточен для уведомления всех пострадавших.
Runbook задаёт отдельное уведомление об инциденте и проверяемый порядок
сверки/разрешения отправок. Числовой epoch не вводится.

## 12. E9 — проверки отказов и выпуск

Проверки поведения пишутся вместе с соответствующими этапами; здесь они
собираются в один воспроизводимый сценарий на готовой конфигурации.

| Сценарий | Ожидаемый результат |
|---|---|
| Падение после commit pending, до HTTP | Новый worker отправляет сохранённые байты и тот же ID |
| Endpoint принял запрос, ACK не сохранён | Допустимый повтор с прежними event ID/webhook-id; один учтённый ACK |
| Старый worker отвечает после передачи lease | Ответ не меняет cursor, pending, retry и не создаёт batch_acked |
| Pause/suspend во время HTTP; отдельно смена URL | В первом случае актуальный ACK допустим; во втором старый lease_token отвергается |
| Смена URL A → B → A, затем ответ старой попытки | Старый ответ отвергается по lease_token; после нового claim используется текущий URL из БД |
| PATCH адресов у active или expired | 409 без изменения набора, версии и статуса |
| Pause/PATCH адресов/resume до завершения старого пустого scan | Старый результат не продвигает cursor; выполняется повтор с новым снимком |
| PATCH адресов или фильтров на паузе при существующем pending | Байты и ID pending прежние; ACK актуальной попытки допустим при старом config_version тела |
| Падение до checkpoint пустого прогресса; затем новый batch | Пустой диапазон сканируется заново; from_cursor берётся из сохранённой позиции |
| Блокировка одной пачки renew и передача части аренд другому worker | Остальные пачки продлеваются; устаревшие token не продлены, без действующей аренды нет новых отправок |
| Resume после изменения адресов, новый claim или несовпадение версии address cache | Перед новым scan загружен полный согласованный снимок адресов и фильтров; без изменений resume не требует повторной загрузки |
| Отдельный failover Postgres или Kvrocks | Head/полнота перепроверяются; источник ждёт, сохранённый pending доступен |
| Failover БД сервиса после подтверждённой записи | Сохраняется рабочее состояние в рамках синхронной HA-конфигурации; проверяется также потеря sync replica |
| Receiver в hot, sender или обязательное body отсутствует | Явное ожидание/остановка; кандидат не пропущен и неполное событие не отправлено |
| Sender в N, receiver только в N+1/N+3, между ними перезапуск | До готовности receiver нет события; затем один event ID по receiver, включая outgoing-подписку |
| Готовый источник, sender найден, записи jetton_transfers нет | Исключение unrecognized_transfer с метрикой, без паузы и без webhook |
| 413, уменьшение max_bytes через PATCH | Подписка остаётся paused; байты/ID pending не изменяются и диапазон не пропускается |
| После 413 исправлен приёмник, исходные блоки уже удалены из hot | Resume доставляет прежний pending из БД; его ACK покрывает сохранённый диапазон |
| Одиночное событие больше max_bytes | Полный одиночный payload; при 413 требуется приёмник с достаточным лимитом |
| Outbox-транзакция с меньшим ID коммитится позже | Потребитель всё равно получает запись; нет max-ID cursor |
| Падение во время ACK батча; повтор ACK; удаление подписки после ACK | Cursor и batch_acked фиксируются атомарно, учёт один и переживает удаление подписки |
| Приватный потребитель упал после сохранения события, до ACK экспорта | Повтор дедуплицируется по outbox ID; учёт и уведомления получают события из общего приватного журнала |
| Восстановление старого pending после уже учтённого ACK | Повторный batch_acked может иметь новый outbox ID; приватный учёт дедуплицирует по webhook_id |
| Перезапуск с тем же Idempotency-Key; конкурентная команда | Прежний результат либо конфликт другого запроса, без второго эффекта |
| Create с `start_mc_seqno="latest"`, head вырос до повтора create и resume | Ответы содержат прежний числовой `start_mc_seqno`; повтор не меняет старт, resume продолжает с сохранённой позиции |
| Восстановление старого backup | До внешнего разрешения нет delivery/test на восстановленные endpoints |

Порядок выпуска: стенд с fixtures → чтение production-источника в shadow
режиме без исходящих вебхуков → ограниченные согласованные endpoints для
обоих потоков → постепенное увеличение подписок. Shadow сравнивает результаты
reader, границы и полноту payload, но не помечает production-батчи принятыми.

Перед canary проверяются алерты и получение управляющих событий приватной
стороной. Расширение допускается после проверки корректности, ресурсоёмкости
и независимости live-доставки от догона. При откате остановить новые отправки,
сохранить pending и БД; версии бинарника должны уметь читать уже
сохранённые состояния. Миграции делать совместимыми с согласованным окном
отката, не применять автоматические разрушительные down migrations.

## 14. Первые изменения для разработки

Начать с трёх небольших результатов, которые можно ревьювить независимо:

1. SQL/fixtures E0 и решение по исторической идентификации поддерживаемых
   jetton-wallets. При необходимости — отдельная доработка writer/индексов.
2. Каркас E1 и общий строгий loader E2 с transaction fixtures. Проверить
   реальную Docker-сборку и отсутствие изменений поведения текущего v3.
3. Миграции и команды Store E4 с конкурентными проверками leases/CAS/ACK.

После этого довести transactions до первого сквозного сценария E5, а jetton
reader E3 разрабатывать на уже проверенном механизме источников. Полноценный
кабинет и массовое подключение клиентов начинаются после закрытия контрактов
E6 и интеграции E8; они не должны задавать семантику доставки постфактум.
